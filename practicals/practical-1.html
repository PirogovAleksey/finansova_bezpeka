Аналіз архітектури FinTech-додатку

⏱ 4 год 📚 До лекцій 1-2 Нова

Мета роботи

Навчитися аналізувати архітектуру типового FinTech веб-додатку з точки зору кібербезпеки. Ви побудуєте діаграму архітектури, визначите потенційні вектори атак, класифікуєте загрози за моделлю STRIDE та запропонуєте конкретні заходи захисту для кожного компонента системи.

Після виконання цієї роботи ви зможете:

  • Будувати архітектурні діаграми FinTech-систем із зазначенням потоків даних
  • Визначати точки входу (entry points) та межі довіри (trust boundaries)
  • Класифікувати загрози за моделлю STRIDE
  • Пропонувати архітектурні рішення для мінімізації ризиків

Теоретичний мінімум

Модель STRIDE — це методологія класифікації загроз, розроблена Microsoft. Кожна літера позначає окремий тип загрози:

  • S — Spoofing (Підміна) — зловмисник видає себе за іншого користувача або систему. Приклад: підроблений API-запит від імені іншого сервісу.
  • T — Tampering (Втручання) — несанкціонована зміна даних. Приклад: зміна суми транзакції під час передачі між сервісами.
  • R — Repudiation (Заперечення) — користувач заперечує виконання дії. Приклад: клієнт каже «я не робив цей переказ», а логів немає.
  • I — Information Disclosure (Витік інформації) — несанкціонований доступ до даних. Приклад: SQL-ін'єкція, що повертає номери карток.
  • D — Denial of Service (Відмова в обслуговуванні) — порушення доступності. Приклад: DDoS на API платіжного шлюзу.
  • E — Elevation of Privilege (Підвищення привілеїв) — отримання прав, яких не повинно бути. Приклад: рядовий оператор отримує доступ адміністратора.

Типова архітектура FinTech-додатку складається з таких основних компонентів:

  • Frontend — веб-додаток або мобільний додаток (React/Angular/Flutter)
  • API Gateway — єдина точка входу для всіх API-запитів, маршрутизація, rate limiting
  • Auth Service — автентифікація та авторизація (OAuth 2.0, JWT, MFA)
  • Payment Service — обробка платежів, інтеграція з платіжними процесорами
  • Transaction Service — ведення транзакцій, бізнес-логіка переказів
  • Database — зберігання даних клієнтів, транзакцій, логів (PostgreSQL/MongoDB)
  • Message Queue — асинхронна комунікація між сервісами (RabbitMQ/Kafka)
  • Third-party APIs — зовнішні сервіси: KYC-провайдер, SWIFT, платіжні мережі

Trust Boundaries (межі довіри) — це логічні межі між зонами з різним рівнем довіри. Наприклад:

  1. Інтернет ↔ API Gateway (зовнішня межа)
  2. API Gateway ↔ Внутрішні сервіси (DMZ ↔ Internal)
  3. Сервіси ↔ База даних (Application ↔ Data)
  4. Внутрішня мережа ↔ Third-party APIs (Internal ↔ External)

На кожній межі довіри повинні бути реалізовані відповідні контролі безпеки: автентифікація, валідація, шифрування, логування.

Опис тестового додатку: «PaySafe»

Для цієї практичної роботи ми використовуємо вигаданий FinTech-додаток «PaySafe» — платформу для P2P-переказів та управління особистими фінансами. Основні функції:

  • Реєстрація та верифікація користувачів (KYC)
  • Поповнення балансу через банківську картку
  • P2P-перекази між користувачами
  • Оплата рахунків та комунальних послуг
  • Історія транзакцій та аналітика витрат
  • Адміністративна панель для операторів

Технологічний стек:

  • Frontend: React SPA, мобільний додаток на Flutter
  • Backend: Node.js (Express) мікросервіси
  • API Gateway: Kong
  • БД: PostgreSQL (транзакції), Redis (сесії, кеш)
  • Черга: RabbitMQ
  • Зовнішні інтеграції: Stripe (прийом платежів), Veriff (KYC), Twilio (SMS/OTP)

Користувачі системи:

  1. Клієнт — кінцевий користувач додатку
  2. Оператор — співробітник підтримки, може переглядати транзакції та блокувати акаунти
  3. Адміністратор — повний доступ до системи, управління користувачами та конфігурацією
  4. Зовнішня система — API партнерів, які інтегруються з PaySafe

Завдання

Завдання 1. Побудова діаграми архітектури (1 год)

Побудуйте Data Flow Diagram (DFD) рівня 1 для додатку PaySafe. Діаграма повинна містити:

  1. Усі основні компоненти системи (frontend, API gateway, сервіси, БД, зовнішні API)
  2. Потоки даних між компонентами (стрілки з описом: «JWT token», «card data», «transaction request» тощо)
  3. Trust boundaries — позначте червоними пунктирними лініями межі довіри
  4. Ролі користувачів та їхні точки входу в систему

Який інструмент обрати

  • draw.io (diagrams.net) — безкоштовний, працює в браузері, має шаблони для DFD та threat models. Найкращий вибір для цієї роботи
  • Excalidraw — швидкий скетч-інструмент, підходить для чернеток. Результат виглядає як «від руки»
  • Miro — підходить для командної роботи, але потребує реєстрації

Поради щодо побудови діаграми

  • Підписуйте стрілки потоків даних: не просто лінія, а «JWT token», «encrypted PAN», «transaction request» — це критично для аналізу загроз
  • Trust boundaries малюйте пунктирними лініями червоного кольору та підписуйте: Internet / DMZ / Internal / Data / External
  • Напрямок стрілок показує напрямок потоку даних, а не виклику. Якщо клієнт надсилає запит — стрілка від клієнта до API Gateway
  • Зовнішні сутності (клієнти, партнери) зображуйте прямокутниками, процеси — колами, сховища даних — паралельними лініями (стандарт DFD)

Результат: файл діаграми у форматі PNG/SVG + короткий опис кожного компонента (2-3 речення).

Завдання 2. Визначення точок входу та вразливостей (1 год)

На основі побудованої діаграми визначте та задокументуйте:

  1. Точки входу (Entry Points) — усі місця, де зовнішні дані потрапляють у систему. Для кожної вкажіть: назву, протокол, тип даних, хто має доступ.
  2. Активи (Assets) — що потрібно захищати. Приклади: дані карток (PAN), PII клієнтів, баланси рахунків, JWT-токени, ключі API.
  3. Потенційні вразливості — для кожної точки входу опишіть мінімум 2 можливих вразливості.

Як знайти всі Entry Points

  • Пройдіться по кожному компоненту на вашій DFD-діаграмі та знайдіть усі стрілки, що входять у систему ззовні
  • Не забудьте про неочевидні входи: WebSocket-з'єднання, webhook-ендпоінти від Stripe/Veriff, файлові завантаження (KYC-документи)
  • Адмін-панель — це окрема точка входу з підвищеними привілеями
  • Для кожної точки входу подумайте: «Що станеться, якщо сюди надіслати неочікувані дані?»

Завдання 3. Класифікація загроз за моделлю STRIDE (1 год)

Для кожного компонента системи визначте загрози за моделлю STRIDE. Заповніть матрицю загроз:

  1. Виберіть 5 ключових компонентів з вашої діаграми
  2. Для кожного компонента визначте, які категорії STRIDE застосовні
  3. Для кожної загрози опишіть: конкретний сценарій атаки, потенційний вплив (Critical / High / Medium / Low), ймовірність реалізації

Як застосовувати STRIDE

Для кожного компонента задайте собі 6 питань:

  1. S — Spoofing: Чи може зловмисник видати себе за цей компонент або за легітимного користувача?
  2. T — Tampering: Чи може хтось змінити дані, які проходять через цей компонент?
  3. R — Repudiation: Чи може користувач заперечити виконання дії? Чи є достатнє логування?
  4. I — Info Disclosure: Чи може компонент випадково розкрити конфіденційні дані?
  5. D — DoS: Чи можна перевантажити або вимкнути цей компонент?
  6. E — Elevation: Чи може звичайний користувач отримати привілеї адміна через цей компонент?

Повний STRIDE-аналіз для API Gateway (зразок)

STRIDE Сценарій атаки Вплив Ймовірність
Spoofing Зловмисник крафтить JWT з вкраденим secret key або використовує алгоритм «none» Critical Medium
Tampering Man-in-the-Middle модифікує HTTP-запит між клієнтом і Gateway (якщо TLS misconfigured) High Low
Repudiation Gateway не логує IP-адресу та User-Agent, неможливо відстежити джерело шкідливих запитів Medium High
Info Disclosure Verbose error messages розкривають внутрішню структуру сервісів (stack trace, internal URLs) Medium High
DoS DDoS-атака на єдину точку входу; відсутність rate limiting дозволяє перевантажити backend Critical High
Elevation Некоректна перевірка ролей: маніпуляція полем «role» в JWT payload дає доступ до /admin/* Critical Medium

Завдання 4. Архітектурні рішення для захисту (1 год)

Для кожної виявленої загрози запропонуйте конкретні архітектурні рішення та контролі безпеки. Структура:

  1. Захист на рівні мережі: сегментація, WAF, DDoS-захист, TLS взаємна автентифікація між сервісами (mTLS)
  2. Захист на рівні додатку: валідація вхідних даних, параметризовані запити, CSP, CORS, secure headers
  3. Захист на рівні даних: шифрування at rest та in transit, токенізація PAN, маскування у логах
  4. Моніторинг та виявлення: централізоване логування (ELK/Splunk), SIEM-правила, алерти на аномалії

Для кожного рішення вкажіть: до якої загрози воно застосовується, конкретну технологію або підхід, та пріоритет впровадження.

Як пов'язати загрози з контролями

  • Кожна загроза з Завдання 3 повинна мати хоча б один захисний захід у цій таблиці
  • Один захід може покривати декілька загроз — вказуйте це явно
  • Пріоритет визначайте за формулою: Вплив × Ймовірність — Critical загрози з високою ймовірністю = Critical пріоритет
  • Вказуйте конкретні технології, а не загальні фрази («використовувати WAF» → «AWS WAF з правилами OWASP Core Rule Set»)

Приклад оформлення роботи

Рекомендована структура вашого звіту:

  1. Титульна сторінка — назва роботи, ПІБ, група, дата
  2. Вступ — мета роботи, короткий опис PaySafe (3-5 речень)
  3. Розділ 1. Діаграма архітектури — DFD Level 1 (вставлене зображення) + текстовий опис кожного компонента

  5. Розділ 3. STRIDE-аналіз — матриця загроз із конкретними сценаріями
  6. Розділ 4. Рекомендації — таблиця захисних заходів із прив'язкою до загроз

Поради щодо оформлення

  • Діаграма: експортуйте у PNG з роздільною здатністю не менше 150 DPI (в draw.io: File → Export as → PNG, Scale 200%)
  • Кольорове кодування: використовуйте червоний для Critical, помаранчевий для High, жовтий для Medium, зелений для Low — це полегшує візуальний аналіз
  • Обсяг звіту: оптимально 8-12 сторінок (без титульної). Більше — не значить краще, цінується конкретика
  • Таблиці: обов'язково нумеруйте таблиці та діаграми (Таблиця 1, Рисунок 1) для зручності посилань
