Apple Pay / Google Pay

NFC-платежі з Secure Element

🔐
Захищений елемент (Secure Element)
Ізольований чіп для Device Account Number. Навіть ОС не має доступу
🔄
Динамічна криптограма (Dynamic Crypto)
Одноразовий криптограм для кожної транзакції, як EMV-чіп
👆
Біометрія
Face ID / Touch ID перед кожним платежем. Перевірка локально
🔒
Конфіденційність (Privacy)
Apple/Google не знають деталей. Merchant не бачить PAN

Open Banking (PSD2)

Банки відкривають API третім сторонам

📊 AISP — доступ до інформації про рахунки (агрегатори фінансів)
💸 PISP — ініціювання платежу з рахунку (оплата без картки)
🔐 SCA — Strong Customer Authentication обов'язкова для всіх операцій
🇺🇦 Україна — НБУ розвиває Open Banking через SEP та API-стандарти

Безпека NFC-платежів

Near Field Communication — технічні деталі

📡 Дальність 1-4 см — фізична близькість як перший фактор безпеки, relay-атака ускладнена
🔐 Secure Element (SE) — ізольований чіп (eSE/UICC/HCE). Зберігає ключі та виконує криптооперації
💳 DPAN — Device PAN, унікальний для пристрою. Реальний PAN не передається через NFC
🔢 CVM limits — до ~500-1500 грн без PIN/біометрії. Вище — обов'язкова верифікація
🛡️ Захист від replay — одноразовий криптограм + sequence counter виключають повторне використання

PSD2 — вимоги SCA

Strong Customer Authentication

🧠
Знання (Knowledge)
Щось, що знає клієнт: PIN, пароль, секретне питання. Перший фактор
📱
Володіння (Possession)
Щось, що має клієнт: телефон (OTP/push), апаратний токен, SIM-картка
👆
Властивість (Inherence)
Щось, чим є клієнт: відбиток пальця, Face ID, голос, поведінкова біометрія
⚡
Виключення SCA
Low-value (<30 EUR), recurring, trusted beneficiary, merchant-initiated, TRA exemption

SCA вимагає мінімум 2 з 3 факторів. Динамічне зв'язування: код прив'язаний до суми та отримувача.

Open Banking API — архітектура

Безпечна взаємодія TPP з банками

1
TPP реєстрація
Ліцензія від регулятора, eIDAS-сертифікат (QWAC/QSeal), реєстрація у банку
2
Запит згоди (Consent Request)
TPP запитує consent через API. Клієнт перенаправляється до банку для підтвердження
3
SCA у банку
Клієнт проходить Strong Customer Authentication безпосередньо у банківському додатку
4
Токен доступу (Access Token)
Банк видає OAuth2 access token з обмеженим scope та терміном дії (90 днів для AIS)
5
API-виклики (API Calls)
TPP працює через RESTful API з mTLS, підписаними запитами (JWS) та rate limiting

Безпека QR-платежів

Загрози та механізми захисту

⚠️
Атака накладання QR (QR Overlay Attack)
Шахрай наклеює свій QR поверх легітимного. Кошти йдуть на рахунок атакуючого
🔗
Фішинговий QR (Phishing QR)
QR веде на фішингову сторінку, що імітує платіжний інтерфейс банку
✅
Цифровий підпис
QR містить ECDSA-підпис від банку. Додаток верифікує перед відображенням деталей
⏱️
Dynamic + TTL
Одноразовий QR з терміном дії 60-300 сек. Прив'язка до суми та merchant ID

EMVCo QR Standard: merchant-presented (статичний/динамічний) та consumer-presented (завжди динамічний, безпечніший).

🛡️

Ключові висновки

1️⃣ Apple/Google Pay — Secure Element + біометрія = безпечніше за картку
2️⃣ QR-платежі — dynamic QR з підписом безпечніше за статичний
3️⃣ Open Banking — PSD2/SCA обов'язкові, Україна рухається до стандарту
4️⃣ e-Wallets — encrypted storage, cert pinning, root detection
