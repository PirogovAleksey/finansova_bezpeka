10.1 Криптогаманці та управління ключами

Криптовалютний гаманець — це інструмент для управління приватними ключами, які дозволяють підписувати транзакції в блокчейні. На відміну від банківських рахунків, у блокчейні немає «забув пароль» — втрата приватного ключа означає безповоротну втрату коштів. За оцінками Chainalysis, понад 20% всіх Bitcoin (>$100 млрд) назавжди втрачені через загублені ключі.

Типи гаманців за зберіганням ключів:

  • Гарячі гаманці (Hot Wallets) — приватний ключ зберігається на пристрої, підключеному до інтернету: мобільні додатки (Trust Wallet, MetaMask Mobile), десктопні (Exodus, Electrum), веб-гаманці (MetaMask browser extension). Зручні для щоденних операцій, але вразливі до шкідливого ПЗ (Malware), фішингу та віддалених атак (Remote Attacks).
  • Холодні гаманці (Cold Wallets) — приватний ключ ніколи не контактує з інтернетом: апаратні гаманці (Hardware Wallets) — Ledger, Trezor; паперові гаманці (Paper Wallets); ізольовані комп'ютери (Air-gapped). Максимальний рівень безпеки, але менш зручні для частих операцій.
  • Кастодіальні гаманці (Custodial Wallets) — ключами управляє третя сторона (біржа, сервіс). Зручно, але «не ваші ключі — не ваші монети» (Not Your Keys, Not Your Coins) — при зломі біржі користувач втрачає кошти (Mt. Gox, FTX).

Сід-фраза (Seed Phrase), або мнемонічна фраза — 12 або 24 слова (BIP-39), що є резервною копією всіх ключів у гаманці. Зберігання: на фізичному носії (металева пластина, папір у сейфі), НІКОЛИ в цифровому вигляді (фото, хмарне сховище, email). Компрометація сід-фрази = втрата всіх коштів.

Мультипідпис (Multisig) — для підписання транзакції потрібно M з N ключів (наприклад, 2 з 3). Використовується корпоративними скарбницями (Treasury), DAO, біржами для захисту від компрометації одного ключа. Gnosis Safe — найпопулярніше рішення для Ethereum мультипідпису.

Багатосторонні обчислення (MPC — Multi-Party Computation) — сучасна альтернатива мультипідпису: приватний ключ розділяється на частки (Shares), які ніколи не збираються разом. Кожна сторона підписує свою частину, і лише комбінація часток утворює валідний підпис. Переваги: сумісність з будь-яким блокчейном, менша вартість газу (Gas Cost), гнучкість у зміні схеми підписання.

Технічний приклад: BIP-39 мнемонічна фраза та HD-гаманець (ієрархічна деривація ключів)

Стандарт BIP-39 визначає генерацію мнемонічної фрази з ентропії, а BIP-32/BIP-44 — ієрархічну деривацію ключів з одного seed. Нижче показано, як з однієї seed-фрази можна отримати необмежену кількість адрес:

# Процес деривації ключів у HD-гаманці (BIP-39 / BIP-32 / BIP-44)
# ==================================================================

# Крок 1: Генерація ентропії (128 біт для 12 слів, 256 біт для 24 слів)
Ентропія (128 біт): 0c1e24e5917779d297e14d45f14e1a1a

# Крок 2: Обчислення контрольної суми (SHA-256, перші 4 біти для 128-біт ентропії)
SHA-256(ентропія) → перші 4 біти = checksum

# Крок 3: Конвертація у мнемонічну фразу (кожне слово = 11 біт, зі словника 2048 слів)
Мнемоніка (12 слів):
  "army van defense carry jealous true garbage claim echo media make crunch"

# Крок 4: Мнемоніка → Seed (PBKDF2-HMAC-SHA512, 2048 ітерацій)
PBKDF2(mnemonic, "mnemonic" + passphrase, 2048, SHA-512)
→ Seed (512 біт): 5b56c417303faa3fcba7e57400e120a0...

# Крок 5: Seed → Master Key (HMAC-SHA512)
HMAC-SHA512(key="Bitcoin seed", data=seed)
→ Master Private Key (256 біт) + Master Chain Code (256 біт)

# Крок 6: Деривація за шляхом BIP-44
# Формат: m / purpose' / coin_type' / account' / change / address_index
#
# Ethereum:  m/44'/60'/0'/0/0  → перша адреса
#            m/44'/60'/0'/0/1  → друга адреса
# Bitcoin:   m/44'/0'/0'/0/0   → перша адреса
# (апостроф ' означає hardened derivation — додатковий захист)

m/44'/60'/0'/0/0 → Private Key → Public Key → Ethereum Address 0xAb5801a7...
m/44'/60'/0'/0/1 → Private Key → Public Key → Ethereum Address 0x1f9840a8...
m/44'/60'/0'/0/2 → Private Key → Public Key → Ethereum Address 0xdAC17F95...

Технічний приклад: Створення гаманця за допомогою ethers.js

Бібліотека ethers.js дозволяє програмно генерувати гаманці, працювати з мнемонічними фразами та підписувати транзакції. Нижче — типовий сценарій створення HD-гаманця:

// Створення та використання Ethereum HD-гаманця (ethers.js v6)
// =============================================================
const { ethers } = require("ethers");

// 1. Створення нового випадкового HD-гаманця з мнемонічною фразою
const wallet = ethers.Wallet.createRandom();
console.log("Мнемонічна фраза:", wallet.mnemonic.phrase);
// Результат: "army van defense carry jealous true garbage claim echo media make crunch"
console.log("Шлях деривації:", wallet.mnemonic.path);
// Результат: "m/44'/60'/0'/0/0"
console.log("Приватний ключ:", wallet.privateKey);
// Результат: "0x4c0883a69102937d623..."
console.log("Адреса:", wallet.address);
// Результат: "0xAb5801a7D398351b8bE11C439..."

// ⚠️ УВАГА: мнемонічну фразу та приватний ключ НІКОЛИ не зберігати у коді!
// Використовувати environment variables або hardware security modules (HSM)

// 2. Відновлення гаманця зі seed-фрази
const mnemonic = "army van defense carry jealous true garbage claim echo media make crunch";
const restoredWallet = ethers.Wallet.fromPhrase(mnemonic);
console.log("Відновлена адреса:", restoredWallet.address);

// 3. Деривація кількох адрес з однієї seed-фрази
const hdNode = ethers.HDNodeWallet.fromPhrase(mnemonic);
for (let i = 0; i < 5; i++) {
  const child = hdNode.deriveChild(i);
  console.log(`Адреса ${i}: ${child.address}`);
}
// Адреса 0: 0xAb5801a7D398351b8bE11C439...
// Адреса 1: 0x1f9840a85d5aF5bf1D1762F925...
// Адреса 2: 0xdAC17F958D2ee523a2206206994...
// Адреса 3: 0x6B175474E89094C44Da98b954E...
// Адреса 4: 0xA0b86991c6218b36c1d19D4a2e...

// 4. Підписання транзакції (без відправки)
const tx = {
  to: "0x1f9840a85d5aF5bf1D1762F925BDADdC4201F984",
  value: ethers.parseEther("0.1"),   // 0.1 ETH
  gasLimit: 21000n,
};
const signedTx = await wallet.signTransaction(tx);
console.log("Підписана транзакція:", signedTx);

Технічний приклад: Multisig транзакція (Gnosis Safe)

Multisig-гаманець вимагає підтвердження від кількох власників перед виконанням транзакції. Ось як виглядає потік 2-з-3 multisig:

// Потік Multisig транзакції (2-з-3, Gnosis Safe SDK)
// ===================================================
const { SafeFactory, SafeAccountConfig } = require("@safe-global/protocol-kit");

// Крок 1: Створення Safe (multisig гаманця) з 3 власниками, поріг = 2
const safeAccountConfig = {
  owners: [
    "0xOwnerA_CFO_address...",     // CFO компанії
    "0xOwnerB_CTO_address...",     // CTO компанії
    "0xOwnerC_Auditor_address..."  // Зовнішній аудитор
  ],
  threshold: 2  // Потрібно 2 з 3 підписів
};
const safeSdk = await SafeFactory.create({ ethAdapter });
const safe = await safeSdk.deploySafe({ safeAccountConfig });
console.log("Safe адреса:", await safe.getAddress());

// Крок 2: CFO ініціює транзакцію (переказ 10 ETH)
const txData = {
  to: "0xRecipient_address...",
  value: ethers.parseEther("10").toString(),
  data: "0x"
};
const safeTx = await safe.createTransaction({ transactions: [txData] });

// Крок 3: CFO підписує (1-й підпис)
const signedByCFO = await safe.signTransaction(safeTx);
// Статус: 1/2 підписів ✓

// Крок 4: CTO перевіряє деталі та підписує (2-й підпис)
const signedByCTO = await safe.signTransaction(signedByCFO);
// Статус: 2/2 підписів ✓✓ — поріг досягнуто!

// Крок 5: Будь-хто з власників виконує транзакцію
const executeTxResponse = await safe.executeTransaction(signedByCTO);
console.log("Tx hash:", executeTxResponse.hash);
// Транзакцію виконано on-chain

// Якщо один з ключів скомпрометовано:
// - Зловмисник має лише 1 з 3 ключів
// - Не може виконати жодної транзакції (потрібно 2)
// - Решта власників можуть замінити скомпрометований ключ

  3. Що означає принцип «не ваші ключі — не ваші монети» (Not Your Keys, Not Your Coins)? Наведіть реальні приклади, коли кастодіальне (Custodial) зберігання призвело до втрати коштів.

10.2 Вразливості смарт-контрактів

Смарт-контракт (Smart Contract) — це програма, що виконується на блокчейні та автоматично реалізує умови угоди. Особливість: після розгортання (Deploy) код є незмінним (Immutable) та публічним. Помилка в коді = вразливість, яку може експлуатувати будь-хто, і виправити її без спеціальних механізмів неможливо.

Найпоширеніші вразливості (за OWASP Smart Contract Top 10):

  • Повторний вхід (Reentrancy) — зловмисний контракт повторно викликає функцію жертви до завершення попереднього виклику. Класичний кейс: злом The DAO (2016) — крадіжка $60 млн ETH через reentrancy, що призвела до форку Ethereum.
  • Цілочисельне переповнення (Integer Overflow/Underflow) — арифметичні помилки при переповненні типу uint256. Наприклад, баланс 0 мінус 1 дає максимальне число замість помилки. Solidity 0.8+ має вбудований захист, але старі контракти вразливі.
  • Контроль доступу (Access Control) — відсутність або неправильна реалізація перевірки прав доступу. Критичні функції (mint, withdraw, pause) без модифікатора onlyOwner доступні будь-кому.
  • Випередження транзакцій (Front-running) — зловмисник бачить очікувану транзакцію в мемпулі (Mempool) та надсилає свою з вищою ціною газу (Gas Price), щоб виконатися першим. Актуально для DEX та аукціонів.
  • Маніпуляція оракулами (Oracle Manipulation) — маніпуляція зовнішніми даними (ціна активу), від яких залежить логіка контракту. Якщо оракул повертає маніпульовану ціну, зловмисник може вилучити кошти з протоколу.
  • Неперевірені повернені значення (Unchecked Return Values) — ігнорування результатів зовнішніх викликів (send, call), що може призвести до продовження виконання при невдалому переказі.

Захист смарт-контрактів:

  • Аудит коду — незалежна перевірка коду спеціалізованими фірмами (Trail of Bits, OpenZeppelin, Consensys Diligence). Мінімум 2 незалежні аудити для DeFi-протоколів з TVL >$10 млн.
  • Формальна верифікація (Formal Verification) — математичний доказ коректності коду. Certora, K Framework дозволяють формально перевірити властивості контракту.
  • Програми винагород за вразливості (Bug Bounty) — Immunefi, HackerOne для безперервного тестування спільнотою. Виплати до $10 млн за критичні вразливості.
  • Використання перевірених бібліотек — OpenZeppelin Contracts як стандарт для ERC-20, ERC-721, access control.

Технічний приклад: Вразливість Reentrancy (паттерн The DAO)

Reentrancy — найвідоміша вразливість смарт-контрактів, яка дозволяє зловмисному контракту повторно викликати функцію жертви до оновлення балансу. Саме ця вразливість була використана у зломі The DAO (2016, $60 млн):

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

// ❌ ВРАЗЛИВИЙ КОНТРАКТ — паттерн The DAO
// ========================================
contract VulnerableVault {
    mapping(address => uint256) public balances;

    function deposit() external payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw() external {
        uint256 amount = balances[msg.sender];
        require(amount > 0, "No balance");

        // ❌ ПОМИЛКА: спочатку відправляємо ETH...
        (bool success, ) = msg.sender.call{value: amount}("");
        require(success, "Transfer failed");

        // ❌ ...і лише ПОТІМ оновлюємо баланс
        // Зловмисний контракт може повторно викликати withdraw()
        // до того, як баланс буде обнулено!
        balances[msg.sender] = 0;
    }
}

// 🔴 КОНТРАКТ ЗЛОВМИСНИКА
contract Attacker {
    VulnerableVault public vault;
    uint256 public attackCount;

    constructor(address _vault) {
        vault = VulnerableVault(_vault);
    }

    function attack() external payable {
        // Крок 1: Вносимо 1 ETH
        vault.deposit{value: 1 ether}();
        // Крок 2: Запускаємо withdraw — спрацює receive()
        vault.withdraw();
    }

    // Ця функція викликається автоматично при отриманні ETH
    receive() external payable {
        if (address(vault).balance >= 1 ether) {
            attackCount++;
            // Повторний виклик withdraw() ДО оновлення балансу!
            vault.withdraw();  // reentrancy!
        }
    }
    // Результат: зловмисник вносить 1 ETH, виводить ВСЕ ETH з контракту
}

// ✅ БЕЗПЕЧНИЙ КОНТРАКТ — паттерн Checks-Effects-Interactions
// ============================================================
contract SecureVault {
    mapping(address => uint256) public balances;

    function deposit() external payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw() external {
        uint256 amount = balances[msg.sender];
        require(amount > 0, "No balance");

        // ✅ Checks: перевірка виконана вище
        // ✅ Effects: СПОЧАТКУ оновлюємо стан
        balances[msg.sender] = 0;

        // ✅ Interactions: і лише ПОТІМ взаємодіємо із зовнішнім контрактом
        (bool success, ) = msg.sender.call{value: amount}("");
        require(success, "Transfer failed");
        // Тепер reentrancy не працює — баланс вже 0
    }
}

// ✅ АЛЬТЕРНАТИВА: використання ReentrancyGuard від OpenZeppelin
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

contract GuardedVault is ReentrancyGuard {
    mapping(address => uint256) public balances;

    function withdraw() external nonReentrant {
        // Модифікатор nonReentrant блокує повторний вхід
        uint256 amount = balances[msg.sender];
        require(amount > 0);
        balances[msg.sender] = 0;
        (bool success, ) = msg.sender.call{value: amount}("");
        require(success);
    }
}

Технічний приклад: Integer Overflow та SafeMath

У Solidity версій до 0.8.0 арифметичні операції не перевіряли переповнення. Це дозволяло зловмисникам маніпулювати балансами:

// Integer Overflow/Underflow — вразливість у Solidity < 0.8.0
// =============================================================

// ❌ ВРАЗЛИВИЙ КОНТРАКТ (Solidity < 0.8.0)
pragma solidity ^0.7.0;

contract VulnerableToken {
    mapping(address => uint256) public balances;

    function transfer(address to, uint256 amount) external {
        // ❌ Якщо balances[msg.sender] = 0 і amount = 1:
        // 0 - 1 = 2^256 - 1 = 115792089237316195423570985008687...
        // Замість помилки — астрономічний баланс!
        balances[msg.sender] -= amount;  // UNDERFLOW!
        balances[to] += amount;

        // ❌ Ще приклад overflow:
        // uint256 max = type(uint256).max;  // 2^256 - 1
        // max + 1 = 0   ← overflow, «обнуляє» баланс
    }
}

// ✅ ЗАХИСТ: бібліотека SafeMath (для Solidity < 0.8.0)
import "@openzeppelin/contracts/math/SafeMath.sol";

contract SafeToken {
    using SafeMath for uint256;
    mapping(address => uint256) public balances;

    function transfer(address to, uint256 amount) external {
        // ✅ SafeMath перевіряє overflow/underflow і відкидає транзакцію
        balances[msg.sender] = balances[msg.sender].sub(amount); // revert якщо underflow
        balances[to] = balances[to].add(amount);                 // revert якщо overflow
    }
}

// ✅ Solidity 0.8.0+ — автоматична перевірка (SafeMath більше не потрібний)
pragma solidity ^0.8.0;

contract ModernToken {
    mapping(address => uint256) public balances;

    function transfer(address to, uint256 amount) external {
        // Автоматичний revert при overflow/underflow
        balances[msg.sender] -= amount;  // безпечно з 0.8.0+
        balances[to] += amount;          // безпечно з 0.8.0+
    }

    // ⚠️ УВАГА: unchecked {} блоки обходять цей захист!
    // Використовувати unchecked тільки для оптимізації gas
    // коли overflow неможливий за логікою програми
    function unsafeIncrement(uint256 x) pure external returns (uint256) {
        unchecked { return x + 1; }  // ← overflow можливий!
    }
}

Технічний приклад: Вразливість Access Control

Відсутність або неправильна реалізація контролю доступу дозволяє будь-кому викликати привілейовані функції контракту:

// Access Control — критична вразливість смарт-контрактів
// ======================================================

// ❌ ВРАЗЛИВИЙ КОНТРАКТ — відсутня перевірка доступу
contract VulnerableDAO {
    mapping(address => uint256) public balances;
    address public owner;
    bool public paused;

    constructor() { owner = msg.sender; }

    // ❌ Будь-хто може викликати mint та створити собі токени!
    function mint(address to, uint256 amount) external {
        balances[to] += amount;
    }

    // ❌ Будь-хто може поставити контракт на паузу!
    function pause() external {
        paused = true;
    }

    // ❌ Будь-хто може змінити власника!
    function setOwner(address newOwner) external {
        owner = newOwner;
    }
}

// ✅ БЕЗПЕЧНИЙ КОНТРАКТ — з OpenZeppelin AccessControl
import "@openzeppelin/contracts/access/AccessControl.sol";

contract SecureDAO is AccessControl {
    mapping(address => uint256) public balances;

    bytes32 public constant MINTER_ROLE = keccak256("MINTER_ROLE");
    bytes32 public constant PAUSER_ROLE = keccak256("PAUSER_ROLE");

    bool public paused;

    constructor() {
        // Засновник отримує роль адміністратора
        _grantRole(DEFAULT_ADMIN_ROLE, msg.sender);
        _grantRole(MINTER_ROLE, msg.sender);
        _grantRole(PAUSER_ROLE, msg.sender);
    }

    // ✅ Тільки адреси з MINTER_ROLE можуть створювати токени
    function mint(address to, uint256 amount) external onlyRole(MINTER_ROLE) {
        balances[to] += amount;
    }

    // ✅ Тільки адреси з PAUSER_ROLE можуть ставити на паузу
    function pause() external onlyRole(PAUSER_ROLE) {
        paused = true;
    }

    // ✅ Передача ролей через стандартний механізм AccessControl
    // grantRole(), revokeRole(), renounceRole()
}

10.3 Безпека DeFi-протоколів

Децентралізовані фінанси (DeFi) — фінансові послуги на блокчейні без посередників: кредитування, обмін, деривативи. Загальна заблокована вартість (TVL — Total Value Locked) у DeFi перевищувала $100 млрд. Водночас DeFi — найбільш атакований сегмент крипто: у 2022-2023 роках зломи DeFi принесли збитки понад $3 млрд.

Атаки миттєвих позик (Flash Loan):

  • Миттєва позика (Flash Loan) — кредит, який береться та повертається в одній транзакції (без застави). Легітимне використання: арбітраж, рефінансування.
  • Атака: зловмисник бере миттєву позику на мільйони доларів → маніпулює ціну на DEX → використовує маніпульовану ціну в іншому протоколі → повертає кредит з прибутком. Все в одній атомарній (Atomic) транзакції.
  • Захист: використання середньозваженої ціни за часом (TWAP — Time-Weighted Average Price) замість спотової ціни (Spot Price), Chainlink як надійний оракул.

Вивід ліквідності (Rug Pull) та шахрайство з виходом (Exit Scam):

  • Rug Pull — розробники створюють токен, залучають ліквідність, а потім виводять всі кошти з пулу. У 2021 році такі схеми склали $2.8 млрд збитків.
  • Ознаки: анонімна команда, немає аудиту, необмежені права карбування (Mint), можливість зміни комісій, заблокована ліквідність (Locked Liquidity) відсутня.
  • Захист: перевірка контракту на TokenSniffer/GoPlus, заблокована ліквідність, відмова від прав власника (Renounced Ownership), наявність аудиту.

Атаки на мости (Bridge Attacks) — атаки на міжмережеві мости (Cross-chain Bridges), які є одними з найвразливіших точок DeFi:

  • Ronin Bridge (2022) — $625 млн: компрометація 5 з 9 валідаторів через social engineering.
  • Wormhole (2022) — $320 млн: вразливість у верифікації підписів.
  • Nomad Bridge (2022) — $190 млн: помилка в ініціалізації, що дозволила будь-кому вивести кошти.

Технічний приклад: Flash Loan атака (псевдокод)

Flash loan атака використовує безкоштовний кредит без застави для маніпуляції цінами та вилучення коштів з протоколів. Вся атака відбувається в одній atomic транзакції:

// Flash Loan атака — псевдокод типової атаки
// =============================================
// Мета: маніпуляція ціни токена на DEX для вилучення коштів з lending протоколу

contract FlashLoanAttacker {
    // Крок 0: Початковий капітал зловмисника = $0

    function executeAttack() external {
        // КРОК 1: Взяти flash loan 10,000 ETH (≈$30M) з Aave
        // Умова: повернути 10,000 ETH + 0.09% комісія в цій же транзакції
        aaveLendingPool.flashLoan(
            address(this),      // отримувач
            WETH,               // актив
            10_000 ether,       // сума
            ""                  // параметри
        );
    }

    // Ця функція автоматично викликається Aave після отримання кредиту
    function executeOperation(
        address asset,
        uint256 amount,       // 10,000 ETH
        uint256 premium,      // 9 ETH (0.09% комісія)
        address initiator
    ) external returns (bool) {

        // КРОК 2: Скинути 5,000 ETH на DEX (Uniswap пул ETH/TOKEN_X)
        // Це ОБВАЛЮЄ ціну TOKEN_X відносно ETH
        uniswapRouter.swapExactTokensForTokens(
            5000 ether,         // продаємо 5000 ETH
            0,                  // мін. вихід (без обмеження)
            [WETH, TOKEN_X],    // шлях обміну
            address(this),
            deadline
        );
        // Ціна TOKEN_X на Uniswap: $100 → $2 (маніпульована)

        // КРОК 3: На lending протоколі, що використовує Uniswap як oracle,
        // TOKEN_X тепер «коштує» $2 замість $100
        // Ліквідувати позиції інших користувачів за заниженою ціною
        // або взяти кредит з мінімальною заставою
        lendingProtocol.borrow(
            WETH,              // беремо ETH
            8000 ether,        // сума кредиту
            TOKEN_X,           // застава (оцінена за маніпульованою ціною)
            myTokenXBalance    // використовуємо дешево куплений TOKEN_X
        );

        // КРОК 4: Повернути ціну до нормальної (продати TOKEN_X назад)
        uniswapRouter.swapExactTokensForTokens(
            tokenXBalance, 0, [TOKEN_X, WETH], address(this), deadline
        );

        // КРОК 5: Повернути flash loan + комісію
        IERC20(WETH).approve(address(aaveLendingPool), amount + premium);
        // Повертаємо 10,009 ETH

        // ПРИБУТОК зловмисника: ~3,000 ETH ($9M)
        // Час атаки: 1 транзакція, ~15 секунд
        return true;
    }
}

Технічний приклад: Oracle Manipulation

Маніпуляція оракулами — ключовий вектор атак на DeFi. Порівняння вразливого та безпечного підходів:

// Oracle Manipulation — вразливий vs безпечний підхід
// ====================================================

// ❌ ВРАЗЛИВИЙ: використання spot price з Uniswap як oracle
contract VulnerableLending {
    IUniswapV2Pair public pair;  // Пул ETH/USDC на Uniswap

    function getPrice() public view returns (uint256) {
        // ❌ Spot price — можна маніпулювати flash loan-ом!
        (uint112 reserve0, uint112 reserve1, ) = pair.getReserves();
        // price = reserve1 / reserve0
        return (uint256(reserve1) * 1e18) / uint256(reserve0);
        // Зловмисник може тимчасово змінити reserves одним swap-ом
    }

    function borrow(uint256 collateralAmount) external {
        uint256 price = getPrice();  // ← маніпульована ціна!
        uint256 borrowAmount = collateralAmount * price / 1e18;
        // Зловмисник отримує кредит за штучно завищеною ціною застави
        _transfer(msg.sender, borrowAmount);
    }
}

// ✅ БЕЗПЕЧНИЙ: використання Chainlink Price Feeds
import "@chainlink/contracts/src/v0.8/interfaces/AggregatorV3Interface.sol";

contract SecureLending {

    constructor() {

        priceFeed = AggregatorV3Interface(
            0x5f4eC3Df9cbd43714FE2740f5E3616155c5b8419
        );
    }

    function getPrice() public view returns (uint256) {
        (
            /* uint80 roundID */,
            int256 price,       // Ціна з 8 десятковими знаками
            /* uint startedAt */,
            uint256 updatedAt,
            /* uint80 answeredInRound */
        ) = priceFeed.latestRoundData();

        // ✅ Перевірка свіжості даних (не старіше 1 години)

// ✅ АЛЬТЕРНАТИВА: TWAP (Time-Weighted Average Price) від Uniswap V3
// Середньозважена ціна за період — неможливо маніпулювати в одній транзакції
contract TWAPOracle {
    IUniswapV3Pool public pool;

    function getTWAPPrice(uint32 twapInterval) external view returns (uint256) {
        // Отримуємо накопичені tick-значення за останні N секунд
        uint32[] memory secondsAgos = new uint32[](2);
        secondsAgos[0] = twapInterval;  // N секунд тому
        secondsAgos[1] = 0;             // зараз

        (int56[] memory tickCumulatives, ) = pool.observe(secondsAgos);

        // Середній tick за період
        int56 tickCumulativesDelta = tickCumulatives[1] - tickCumulatives[0];
        int24 avgTick = int24(tickCumulativesDelta / int56(int32(twapInterval)));

        // Конвертація tick → price
        // Маніпуляція TWAP вимагає підтримки штучної ціни протягом
        // ВСЬОГО періоду — економічно невигідно
        return getQuoteAtTick(avgTick, 1e18, WETH, USDC);
    }
}

10.4 Безпека бірж та регулювання

Централізовані біржі (CEX) — основна точка входу користувачів у крипто. Вони зберігають мільярди доларів у криптоактивах, що робить їх привабливою мішенню для хакерів та шахраїв.

Безпека біржової інфраструктури:

  • Розподіл холодного/гарячого сховища (Cold/Hot Storage) — 95%+ активів у холодному сховищі (мультипідпис, HSM), лише 5% у гарячому гаманці для операційної ліквідності.
  • Підтвердження резервів (Proof of Reserves, PoR) — криптографічне підтвердження наявності активів на біржі. Дерево Меркла (Merkle Tree) + аудитор. Після краху FTX PoR став де-факто стандартом.
  • Безпека виведення коштів (Withdrawal Security) — білий список адрес (Whitelist), період охолодження (Cooling Period) для нових адрес (24-72 години), MFA, email-підтвердження, ліміти виведення.
  • Страхові фонди (Insurance Funds) — резервні фонди для компенсації збитків (Binance SAFU fund — $1 млрд).

Регулювання криптоактивів:

  • EU MiCA (Markets in Crypto-Assets) — перший комплексний регуляторний фреймворк для крипто в ЄС. Вимоги до ліцензування, AML, custody, stablecoin reserves, consumer protection.
  • Правило подорожі (Travel Rule, FATF Recommendation 16) — при переказі криптоактивів понад поріг ($1000) біржі повинні обмінюватися інформацією про відправника та отримувача, аналогічно банківським переказам.
  • Україна — Закон «Про віртуальні активи» (2022) встановлює правовий фреймворк, НКЦБФР як регулятор, вимоги до реєстрації та AML-compliance для VASP (Virtual Asset Service Providers).

Технічний приклад: Proof of Reserves (Merkle Tree верифікація)

Proof of Reserves дозволяє біржі криптографічно довести, що вона має достатні резерви для покриття депозитів користувачів, без розкриття індивідуальних балансів. Використовується Merkle Tree:

# Proof of Reserves — верифікація за допомогою Merkle Tree
# =========================================================
import hashlib
import json

class MerkleProofOfReserves:
    """
    Біржа будує Merkle Tree з хешів (user_id + balance).
    Кожен користувач може перевірити, що його баланс включено в дерево,
    не бачачи балансів інших користувачів.
    """

    @staticmethod
    def hash_node(data: str) -> str:
        return hashlib.sha256(data.encode()).hexdigest()

    @staticmethod
    def hash_pair(left: str, right: str) -> str:
        combined = left + right
        return hashlib.sha256(combined.encode()).hexdigest()

    def build_tree(self, user_balances: list) -> dict:
        """
        user_balances = [
            {"user_id": "hash_user_A", "balance": 1.5},   # 1.5 BTC
            {"user_id": "hash_user_B", "balance": 0.8},   # 0.8 BTC
            {"user_id": "hash_user_C", "balance": 3.2},   # 3.2 BTC
            {"user_id": "hash_user_D", "balance": 0.5},   # 0.5 BTC
        ]
        Total reserves: 6.0 BTC
        """
        # Крок 1: Створити leaf-вузли (хеші балансів)
        leaves = []
        for ub in user_balances:
            leaf = self.hash_node(f"{ub['user_id']}:{ub['balance']}")
            leaves.append(leaf)

        # Крок 2: Побудувати дерево знизу вгору
        #
        #              Merkle Root
        #             /            \
        #        Hash(AB)        Hash(CD)
        #       /       \       /       \
        #   Hash(A)  Hash(B) Hash(C)  Hash(D)
        #      |        |       |        |
        #  User_A:1.5 User_B:0.8 User_C:3.2 User_D:0.5
        #
        tree = [leaves]
        current_level = leaves

        while len(current_level) > 1:
            next_level = []
            for i in range(0, len(current_level), 2):
                left = current_level[i]
                right = current_level[i + 1] if i + 1 < len(current_level) else left
                next_level.append(self.hash_pair(left, right))
            tree.append(next_level)
            current_level = next_level

        merkle_root = current_level[0]
        return {"root": merkle_root, "tree": tree, "total_reserves": sum(u['balance'] for u in user_balances)}

    def generate_proof(self, tree, index: int) -> list:
        """Генерує Merkle proof для конкретного користувача"""
        proof = []
        for level in tree["tree"][:-1]:
            if index % 2 == 0:
                sibling_idx = index + 1 if index + 1 < len(level) else index
                proof.append({"position": "right", "hash": level[sibling_idx]})
            else:
                proof.append({"position": "left", "hash": level[index - 1]})
            index //= 2
        return proof

    def verify_proof(self, leaf_hash: str, proof: list, root: str) -> bool:
        """Користувач верифікує, що його баланс включено в дерево"""
        current = leaf_hash
        for step in proof:
            if step["position"] == "left":
                current = self.hash_pair(step["hash"], current)
            else:
                current = self.hash_pair(current, step["hash"])
        return current == root  # True = баланс підтверджено!

# === Приклад використання ===
por = MerkleProofOfReserves()

# Біржа публікує Merkle Root та загальну суму резервів
balances = [
    {"user_id": "sha256(user_a@email.com + nonce)", "balance": 1.5},
    {"user_id": "sha256(user_b@email.com + nonce)", "balance": 0.8},
    {"user_id": "sha256(user_c@email.com + nonce)", "balance": 3.2},
    {"user_id": "sha256(user_d@email.com + nonce)", "balance": 0.5},
]
tree = por.build_tree(balances)
print(f"Merkle Root: {tree['root']}")
print(f"Загальні резерви: {tree['total_reserves']} BTC")

# Аудитор перевіряє: on-chain баланс гаманця біржі >= total_reserves
# Кожен користувач верифікує свій proof:
proof = por.generate_proof(tree, index=0)  # proof для User A
leaf = por.hash_node("sha256(user_a@email.com + nonce):1.5")
is_valid = por.verify_proof(leaf, proof, tree["root"])
print(f"User A баланс підтверджено: {is_valid}")  # True

Підсумок

Безпека криптоактивів вимагає розуміння унікальних ризиків: незворотність транзакцій, публічність та незмінність смарт-контрактів, відсутність централізованого захисту. Управління приватними ключами через холодне сховище (Cold Storage), мультипідпис (Multisig) та багатосторонні обчислення (MPC) є фундаментом безпеки.

Смарт-контракти вразливі до повторного входу (Reentrancy), маніпуляції оракулами (Oracle Manipulation) та помилок контролю доступу (Access Control) — аудит коду та формальна верифікація (Formal Verification) є обов'язковими. DeFi-протоколи потерпають від атак миттєвих позик (Flash Loan), виводу ліквідності (Rug Pull) та зломів мостів (Bridge Exploits). Регулювання (MiCA, правило подорожі) поступово приводить крипто-індустрію до стандартів традиційних фінансів.

У наступній лекції ми розглянемо AML та фінансовий моніторинг: протидію відмиванню коштів, KYC-процедури, системи transaction monitoring та міжнародні стандарти FATF.
