Шифрування даних

Багаторівневий захист фінансових даних

💾
У стані спокою (At Rest / TDE)
Файли БД зашифровані на диску. Oracle TDE, SQL Server TDE, pgcrypto
🔄
При передачі (In Transit)
TLS/SSL між додатком та БД. За замовчуванням — відкритий текст!
📊
На рівні стовпців (Column-level)
Окремі стовпці: PAN, CVV, SSN. Навіть DBA не бачить
🏗️
На рівні додатку (Application-level)
Шифрування ДО збереження. Компрометація БД не дає дані

Розмежування доступу

🔑 Мінімальні привілеї (Least Privilege): сервіс аналітики — тільки SELECT, платежі — SELECT/INSERT/UPDATE
📊 Безпека на рівні рядків (RLS): менеджер бачить лише клієнтів свого відділення
🎭 Динамічне маскування (Dynamic Masking): call-центр бачить **** **** **** 1234 замість повного PAN
🚫 Без прямого доступу (No direct access): розробники — через затверджені інструменти з аудитом

Окремий DB user для кожного мікросервісу. Сервіс нотифікацій НЕ потребує доступу до таблиці transactions.

Моніторинг активності бази даних (DAM)

Виявлення аномальних запитів

🚨
Масовий експорт (Mass Export)
SELECT * з таблиці мільйонів клієнтів — аларм!
🌙
Позаробочий час (Off-hours)
Запити до production о 3:00 AM — підозріло
🔧
Зміни DDL (DDL Changes)
ALTER TABLE, DROP — повинні бути заплановані
📋
Журнал аудиту (Audit Trail)
IBM Guardium, Imperva, Oracle Audit Vault

Безпека резервних копій

Backup = повна копія ВСІХ даних

🔐 Шифрування: AES-256 для всіх backup-файлів
🔑 Доступ: окремі credentials для backup storage
🌍 Географічне розділення (Geo-separation): backup в іншій локації/регіоні
🧪 Тестування: регулярне відновлення для перевірки цілісності

Кейс 2020: незашифрований backup PostgreSQL банку → публічний S3 bucket → 500K клієнтів скомпрометовано.

PCI DSS для баз даних

Обов'язкові вимоги для карткових даних

3️⃣ Req 3: Шифрувати PAN at rest. Ніколи не зберігати CVV після авторизації
4️⃣ Req 4: Шифрування in transit через TLS 1.2+ для карткових даних
7️⃣ Req 7: Доступ до карткових даних тільки за business need-to-know
🔟 Req 10: Логування та моніторинг всього доступу до карткових даних

Штрафи PCI DSS за невідповідність (non-compliance): $5,000 — $100,000 на місяць. Плюс відповідальність за витік.

Токенізація (Tokenization)

Заміна PAN на безпечний токен

1
PAN → Vault
Реальний номер картки зберігається у захищеному сховищі
2
Токенізація (Token)
Замість PAN видається випадковий токен
3
Використання
Додаток працює з токеном, не з PAN
4
Детокенізація
Лише при оплаті — PAN повертається процесору

Токенізація зменшує обсяг вимог PCI DSS: більшість систем ніколи не бачать реальний PAN.

Шифрування: у стані спокою vs при передачі

Два обов'язкових рівні захисту даних

💾
У стані спокою (At Rest)
TDE — прозоре шифрування файлів БД
AES-256 — стандарт для фінансів
Захист від крадіжки дисків/backup
Управління ключами (Key Management) — HSM або KMS
Oracle TDE, SQL Server TDE, LUKS
🔄
При передачі (In Transit)
TLS 1.2+ між додатком та БД
Закріплення сертифіката (Certificate pinning) для DB-з'єднань
Захист від перехоплення (MITM)
За замовчуванням — відкритий текст!
mTLS для production середовищ

PCI DSS вимагає ОБИДВА рівні: шифрування PAN на диску (Req 3) та TLS для передачі (Req 4).

Аудит-логування бази даних

Конфігурація для фінансових систем

📝 Що логувати: всі SELECT/INSERT/UPDATE/DELETE до таблиць з PII та фінансовими даними
👤 Хто виконав: DB user, IP-адреса, application name, session ID
⏰ Коли: timestamp з точністю до мілісекунд, timezone UTC
🔒 Захист логів: окремий сервер, лише дозапис (append-only), WORM-сховище, підпис хешами
📊 Інструменти: pgAudit (PostgreSQL), MySQL Audit Plugin, Oracle Audit Vault, SQL Server Audit

PCI DSS Req 10: зберігати аудит-логи мінімум 1 рік, з яких 3 місяці — миттєво доступні для аналізу.

Безпека на рівні рядків (RLS)

Обмеження доступу на рівні рядків

1
Політика
CREATE POLICY — визначає, хто бачить які рядки
2
Контекст
current_user, session variable (branch_id, role)
3
Фільтрація
БД автоматично додає WHERE branch_id = current_branch
4
Прозорість
Додаток не знає про обмеження — БД гарантує безпеку

Банківський приклад: менеджер відділення №5 бачить лише клієнтів відділення №5. Навіть через SQL-клієнт.

Чекліст безпеки backup

Резервна копія = повна копія ВСІХ даних

🔐
Шифрування
AES-256 для всіх backup-файлів. Ключі окремо від даних. Ротація ключів щоквартально
🔑
Доступ
Окремі credentials. MFA для відновлення. Principle of dual control — 2 особи
🌍
Зберігання
Географічне розділення: інший регіон/дата-центр. Незмінне сховище (WORM). Політика зберігання
🧪
Тестування
Щомісячне відновлення. Перевірка цілісності хешами. RTO/RPO метрики

Правило 3-2-1: 3 копії даних, на 2 різних типах носіїв, 1 копія offsite. Для фінтех — 3-2-1-1-0 (1 offline, 0 помилок).

🛡️

Ключові висновки

1️⃣ Шифрування — у стані спокою + при передачі + на рівні стовпців для PAN/CVV
2️⃣ Мінімальні привілеї (Least Privilege) — окремий DB user для кожного сервісу
3️⃣ Моніторинг — DAM для виявлення аномалій та аудиту
4️⃣ Токенізація (Tokenization) — замінює PAN токеном, зменшує обсяг PCI DSS
