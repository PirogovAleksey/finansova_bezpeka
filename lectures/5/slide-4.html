Підготовлені запити (Prepared Statements)

Єдиний надійний захист від SQLi

❌
Конкатенація
"SELECT * WHERE id='" + input + "'"
Дані = частина SQL-коду
Ін'єкція можлива
НІКОЛИ не використовувати
✅
Параметризація
"SELECT * WHERE id = ?"
Дані передаються окремо
Ніколи не інтерпретуються як код
100% запитів — без виключень

PDO (PHP), PreparedStatement (Java), psycopg2 (Python), pg (Node.js) — всі підтримують параметризацію.

Міжмережевий екран додатків (WAF)

Додатковий шар, НЕ заміна безпечного коду

📝
На основі сигнатур (Signature-based)
Відомі патерни: UNION SELECT, <script>, ../etc/passwd
📊
Виявлення аномалій (Anomaly Detection)
Незвично довгі параметри, нетипові символи, частота
🩹
Віртуальне патчування (Virtual Patching)
Блокування відомої CVE до виправлення коду. Критично для legacy
🔧
Рішення
AWS WAF, Cloudflare, ModSecurity, F5 Advanced WAF

WAF обходиться через кодування (encoding), фрагментацію, альтернативний синтаксис. Не покладайтесь лише на WAF!

Валідація вхідних даних (Input Validation)

Білий список — дозволяйте лише відоме безпечне

📋 Формат: IBAN — UA + 27 цифр, Email — RFC 5322, Phone — E.164
🔢 Тип: amount — число з 2 десятковими, account_id — integer
📏 Довжина: коментар max 140 символів, ім'я max 100
💼 Бізнес-логіка: amount > 0, відправник ≠ отримувач, достатній баланс

Валідувати ВСІ вхідні дані. Currency IN ['UAH','USD','EUR'] — не довіряти клієнту.

Найкращі практики ORM (Best Practices)

✅ Конструктори запитів (Query builders) — Model.where(name: params[:name]) замість raw SQL
❌ Без інтерполяції — Model.where("name = '#{input}'") = вразливо!
⚠️ Динамічні запити — обережно з Model.where(params[:filter])
🔄 Оновлення — регулярно оновлювати ORM, вразливості є і в Hibernate

ORM дає зручність, але НЕ автоматичний захист. Прямі запити (raw queries) та інтерполяція рядків = ін'єкція.

Зміцнення бази даних (Database Hardening)

Захищена конфігурація СУБД

🔑
Облікові дані (Credentials)
Змінити default паролі. Унікальні credentials для кожного сервісу
🚫
Вимкнення невикористовуваних (Disable Unused)
xp_cmdshell, LOAD_FILE, UTL_HTTP — вимкнути все зайве
🌐
Мережевий рівень (Network)
БД не виставляти в інтернет. Тільки внутрішня мережа + firewall

CIS Benchmarks — готові чеклісти hardening для MySQL, PostgreSQL, Oracle, MSSQL. Використовуйте їх.

Багаторівневий захист серверної частини

Параметризовані запити: 3 мови

Практичні приклади безпечного коду

🐍
Python (psycopg2)
cursor.execute(
"SELECT * FROM accounts WHERE id = %s",
(user_id,))

Параметр %s — НІКОЛИ f-string!
☕
Java (JDBC)
PreparedStatement ps = conn.prepareStatement(
"SELECT * FROM accounts WHERE id = ?");
ps.setInt(1, userId);

Параметр ? — типобезпечний
🟢
Node.js (pg)
pool.query(
'SELECT * FROM accounts WHERE id = $1',
[userId])

Параметр $1 — масив значень

Одне правило для всіх мов: SQL-запит і дані ЗАВЖДИ передаються окремо. Жодної конкатенації.

WAF: приклади правил

Типові правила для захисту фінансових API

🚫 SQLi сигнатури: блокування UNION SELECT, OR 1=1, WAITFOR DELAY, '; DROP TABLE
📏 Обмеження частоти (Rate limiting): max 100 запитів/хв на IP, max 10 невдалих логінів за 5 хв
🌍 Геоблокування (Geo-blocking): блокування трафіку з країн без клієнтів, білий список для API партнерів
📊 Оцінка аномалій (Anomaly scoring): кожна підозріла ознака додає бали, поріг = блокування
🩹 Віртуальне патчування (Virtual patching): спеціальне правило для конкретної CVE до патчу додатку

ModSecurity CRS, AWS WAF Managed Rules, Cloudflare OWASP Ruleset — готові набори правил для старту.

Ешелонований захист: архітектура

Багатошарова модель захисту фінансової системи

1
Периметр (Edge / CDN / WAF)
Захист від DDoS, WAF правила, обмеження частоти, геоблокування
2
API Gateway
Автентифікація, авторизація, валідація вводу, валідація схеми
3
Прикладний рівень (Application)
Підготовлені запити, ORM, валідація бізнес-логіки, кодування виводу
4
Рівень БД (Database)
Мінімальні привілеї, RLS, шифрування, аудит-логування, зміцнення

Принцип: компрометація одного шару НЕ дає доступу до даних. Кожен шар — незалежний бар'єр.

DevSecOps: безпека інтегрована в кожен етап розробки, а не додається наприкінці.

Code Review для безпеки

Ревізія коду як засіб запобігання вразливостям

🔍 Обов'язкова ревізія — кожен код, що взаємодіє з БД, проходить code review
🤖 Автоматизація — виявляє очевидні патерни (конкатенація рядків, інтерполяція в SQL)
👤 Людський рецензент — логічні помилки, бізнес-вразливості, second-order SQLi
👥 Два незалежні рецензенти — обов'язково для коду обробки платежів

Автоматизація + людська ревізія = комплементарний підхід до безпеки коду.

WAF: режими роботи

Inline vs Monitoring — два підходи до впровадження

🛑
Inline (блокування)
Підозрілі запити негайно відхиляються
Активний захист у реальному часі
Ризик false positives — блокування легітимного трафіку
👁️
Monitoring (спостереження)
Запити фіксуються в журналах без блокування
Аналіз перед активацією правил
Безпечний старт для нових правил

False positives: SWIFT-повідомлення з SQL-подібним синтаксисом може бути заблоковане. Нові правила запускати в monitoring на тижні.

Configuration Drift

Дрейф конфігурації — прихована загроза безпеці БД

1
Безпечний стан
Hardening за CIS Benchmarks — початкова захищена конфігурація
2
Дрейф
Оновлення СУБД, екстрені зміни, тимчасові послаблення безпеки
3
Накопичення
Відхилення від безпечних налаштувань з часом стають критичними
4
Compliance Scanning
OpenSCAP, Qualys, AWS Config — безперервний моніторинг відповідності

Зміцнення БД — не одноразовий захід, а безперервний процес. Автоматичне сканування відповідності — обов'язково.
