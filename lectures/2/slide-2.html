DevSecOps

Безпека — відповідальність кожного

🔄 Зсув вліво (Shift Left) — безпека на початку, а не в кінці розробки
🤖 Автоматизація — перевірки безпеки у кожному CI/CD-конвеєрі (pipeline)
👥 Культура — розробники навчені практикам безпечного кодування (secure coding)
📊 Метрики — середній час виправлення (MTTR), щільність вразливостей (vulnerability density)

DevSecOps = Dev + Sec + Ops. Безпека інтегрована, а не «прикручена» в кінці.

Security Pipeline

Автоматичні перевірки на кожному етапі

🔑 Pre-commit — git-secrets, truffleHog (секрети у коді)
📝 SAST — Semgrep, SonarQube, Checkmarx (статичний аналіз)
📦 SCA (аналіз складу ПЗ) — Snyk, OWASP Dependency-Check (вразливі бібліотеки)
🐳 Container — Trivy, Clair (сканування Docker-образів)
🌐 DAST — OWASP ZAP, Burp Suite (динамічне тестування)
☁️ IaC (інфраструктура як код) — Checkov, tfsec (помилки конфігурації Terraform)

SAST vs DAST

📄
SAST
Статичний аналіз (Static Analysis)
Аналізує код без запуску
Швидко, на кожен commit
Знаходить: SQL-ін'єкції, XSS-патерни, захардкоджені секрети
🌐
DAST
Динамічний аналіз (Dynamic Analysis)
Тестує працюючий додаток
На staging перед prod
Знаходить: обхід автентифікації, IDOR (небезпечні прямі посилання), помилки виконання

IAST (Interactive) = SAST + DAST. Агент всередині додатку аналізує потоки даних у runtime.

SAST vs DAST vs IAST — порівняння

Три підходи до тестування безпеки

📄
SAST
Білий ящик (White-box). Аналіз вихідного коду. Швидко, багато хибних спрацювань. Semgrep, SonarQube
🌐
DAST
Чорний ящик (Black-box). Тестує працюючий додаток ззовні. Реальні вразливості, повільно. OWASP ZAP, Burp
🔬
IAST
Сірий ящик (Grey-box). Агент всередині додатку. Точний, мало хибних спрацювань. Contrast Security, Hdiv
SAST
на кожен commit
DAST
на staging
IAST
QA/staging

Процес Threat Modeling

Покрокове моделювання загроз для FinTech

1
Обсяг (Scope)
Визначити межі системи та діаграму потоків даних (DFD)
2
Ідентифікація (Identify)
Знайти активи: PII, фінансові дані, ключі
3
STRIDE
Для кожного компонента застосувати 6 категорій загроз
4
DREAD
Оцінити ризик: Шкода, Відтворюваність, Експлуатованість, Масштаб, Виявлюваність
5
Пом'якшення (Mitigate)
Визначити контрзаходи для кожної загрози

Threat Model проводиться при кожній зміні архітектури. Для FinTech обов'язково включає PCI DSS та Open Banking загрози.

DevSecOps Pipeline

Повний потік безпеки від коду до production

💻 IDE — плагіни безпеки (Semgrep, Snyk) підказують вразливості під час написання коду
🔑 Pre-commit — git-secrets блокує commit з API-ключами, паролями, приватними ключами
📝 CI Build — SAST + SCA + license check + secret scanning автоматично на кожному PR
🐳 Збірка контейнера (Container Build) — Trivy сканує Docker-образ, Cosign підписує для безпеки ланцюга постачання
🧪 Тестове середовище (Staging) — DAST + IAST + фазинг API на тестовому оточенні перед релізом
🚀 Продакшн (Production) — RASP (захист під час виконання) + WAF (фаєрвол застосунків) + моніторинг + виявлення аномалій

Security Gates в CI/CD

Автоматичні ворота, що блокують небезпечний код

🚫
Блокуючі (Hard Gates)
Critical/High вразливості
Секрети у коді
Вразливі залежності (оцінка CVSS > 7)
Неліцензовані компоненти
Непідписані Docker-образи
⚠️
Попереджуючі (Soft Gates)
Medium/Low вразливості
Проблеми якості коду
Покриття тестами нижче порогу
Застарілі (deprecated) залежності
Прогалини в документації

Hard Gates зупиняють pipeline повністю. У FinTech жодна вразливість рівня Critical не повинна потрапити у production.

Ключові висновки

1️⃣ Shift Left — чим раніше знайдена вразливість, тим дешевше її виправити
2️⃣ Threat Modeling — STRIDE на етапі Design виявляє архітектурні проблеми
3️⃣ Автоматизація — SAST/DAST/SCA у CI/CD = постійний контроль
4️⃣ DevSecOps культура — безпека = відповідальність всієї команди
