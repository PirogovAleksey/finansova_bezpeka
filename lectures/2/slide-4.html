Найпоширеніші вразливості API (2023)

🔓 BOLA — Broken Object Level Authorization (IDOR)
🔑 Порушена автентифікація (Broken Auth) — слабка автентифікація, витік токенів

BOLA — #1 вразливість API

Broken Object Level Authorization

❌
Вразливий код
GET /api/accounts/12345

// Повертає баланс
// account_id з URL
// Без перевірки власника!
✅
Безпечний код
GET /api/accounts/12345

// Перевіряємо:
// account.owner == user.id
// → 403 Forbidden

Зміна account_id в URL НЕ ПОВИННА давати доступ до чужих даних. Завжди перевіряйте права на об'єкт!

OAuth 2.0 для FinTech

Стандарт авторизації API

📱
Код авторизації (Authorization Code) + PKCE
Для мобільних та SPA (односторінкових застосунків). PKCE (захист коду авторизації) захищає від перехоплення
🖥️
Облікові дані клієнта (Client Credentials)
Для server-to-server. Сервіс автентифікується напряму
🎫
Обсяги доступу (Scopes)
read:balance, transfer:create — обмеження прав токена
⏰
Короткоживучі токени (Short-lived tokens)
Токен доступу (Access Token): 15 хв. Токен оновлення (Refresh Token): 7 днів. Ротація обов'язкова

API Gateway — єдина точка входу

🔐 Автентифікація — перевірка JWT/OAuth токенів на вході
⏱️ Обмеження частоти (Rate Limiting) — 100 зап/хв для читання, 5 зап/хв для переказів
📋 Валідація запитів (Request Validation) — перевірка структури за OpenAPI-схемою
🛡️ WAF (фаєрвол застосунків) — блокування SQL-ін'єкцій, XSS, обходу шляху (path traversal)
📊 Журналювання (Logging) — всі запити логуються для аудиту та аналізу

OAuth 2.0 Flows: порівняння

Вибір правильного flow для кожного сценарію

📱
Код авторизації (Auth Code) + PKCE
Мобільні додатки, SPA. Найбезпечніший для публічних клієнтів. PKCE запобігає перехопленню
🖥️
Облікові дані клієнта (Client Credentials)
Server-to-server. Без участі користувача. Ідеально для мікросервісів та batch-процесів
🔄
Код пристрою (Device Code)
Smart TV, IoT-пристрої. Користувач авторизує на іншому пристрої через код
⚠️
Неявний, застарілий (Implicit, deprecated)
НЕ використовувати! Токен у URL, немає refresh. Замінений на Auth Code + PKCE

У FinTech забороняється Implicit Flow та Resource Owner Password. Тільки Authorization Code + PKCE або Client Credentials.

API Security Checklist

Обов'язкові перевірки для кожного FinTech API

🔐 Автентифікація — OAuth 2.0 + JWT з перевіркою підпису, issuer, audience, expiration
🔑 Авторизація — перевірка прав на кожен об'єкт (BOLA) та кожну функцію (BFLA)
📋 Валідація вводу (Input Validation) — перевірка за OpenAPI-схемою, очищення (sanitization), обмеження довжини для всіх полів
⏱️ Обмеження частоти (Rate Limiting) — ліміти на користувача, IP, ендпоінт з плавною деградацією (graceful degradation)
📊 Журналювання (Logging) — кожен запит логується з ідентифікатором кореляції (correlation ID), без чутливих даних у логах
🔒 TLS 1.3 — тільки HTTPS, HSTS (примусовий HTTPS), закріплення сертифіката (certificate pinning) для мобільних

Стратегії Rate Limiting

Захист API від перевантаження та зловживань

🪣
Кошик токенів (Token Bucket)
Токени додаються з фіксованою швидкістю. Дозволяє короткі пікові сплески
🪟
Ковзне вікно (Sliding Window)
Ковзне вікно часу. Точніший підрахунок, запобігає сплеску на межі вікна
📊
Адаптивний (Adaptive)
Динамічні ліміти на основі навантаження сервера та поведінки клієнта
100/хв
читання балансу
5/хв
грошові перекази
3/год
зміна пароля

Відповідь при перевищенні ліміту: HTTP 429 з заголовками Retry-After та X-RateLimit-Reset для коректної роботи клієнтів.
