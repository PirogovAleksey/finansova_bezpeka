Лекція 3.2

JWT, OAuth 2.0, OpenID Connect

Структура JWT

Заголовок (Header) . Навантаження (Payload) . Підпис (Signature)

📋
Заголовок (Header)
Алгоритм (HS256, RS256), тип токена (JWT)
📦
Навантаження (Payload)
sub, iat, exp, ролі, дозволи — закодований Base64, НЕ зашифрований
✍️
Підпис (Signature)
HMAC або RSA підпис — гарантує цілісність токена

Навантаження (Payload) видно кожному! Base64 — це кодування, не шифрування. Ніколи не зберігайте секрети у JWT.

Вразливості JWT

Критичні для фінансових систем

🚫 Атака «без алгоритму» (Algorithm None) — alg: «none» → сервер приймає без підпису
🔄 Плутанина алгоритмів (Algorithm Confusion) — RS256→HS256, підпис публічним ключем як HMAC
⏰ Без терміну дії (No expiration) — відсутній або ігнорований exp = безстроковий доступ
🗑️ Без відкликання (No revocation) — JWT без стану (stateless), скомпрометований токен не анулювати

Рішення: короткий час життя (TTL, 5-15 хв), список дозволених алгоритмів, ротація токенів оновлення (refresh token rotation), чорний список токенів.

OAuth 2.0 для FinTech

Делегована авторизація без передачі пароля

1
Запит авторизації (Authorization Request)
Клієнт → Сервер авторизації
2
Згода користувача (User Consent)
Користувач схвалює доступ
3
Код авторизації (Authorization Code)
Сервер повертає код
4
Обмін на токен (Token Exchange)
Код + PKCE → токен доступу (access token)

Відкритий банкінг (Open Banking): клієнт надає фінтех-додатку доступ до банківського акаунту без розкриття пароля банку.

Потоки OAuth 2.0 (OAuth 2.0 Flows)

📱
Код авторизації + PKCE
Мобільні та SPA-додатки. Найбезпечніший потік для клієнтських додатків
🖥️
Облікові дані клієнта (Client Credentials)
Сервер-сервер. Мікросервіс платежів → сервіс верифікації
🏧
Авторизація пристрою (Device Grant)
Пристрої без браузера: IoT-термінали, банкомати, POS

Неявний потік (Implicit Flow) — ЗАСТАРІЛИЙ! Токен у URL = витік через історію браузера, заголовки referer, логи.

Управління сесіями (Session Management)

Вимоги до сесій у фінансових системах

⏱️ Короткий таймаут — 5-15 хв неактивності для інтернет-банкінгу
🔄 Фіксація сесії (Session fixation) — новий ідентифікатор сесії після кожного входу
🍪 Захищені cookie (Secure cookies) — HttpOnly, Secure, SameSite=Strict
👥 Контроль одночасності (Concurrent control) — 1 активна сесія на оператора
📍 Прив'язка до контексту (Context binding) — прив'язка до IP, User-Agent, відбитку пристрою

JWT — детальна структура

Розбір реального токена банківського API

H
Заголовок / Header (Base64)
{"alg": "RS256", "typ": "JWT", "kid": "bank-key-2025"} — алгоритм + ідентифікатор ключа
P
Навантаження / Payload (Base64)
{"sub": "user-123", "role": "operator", "branch": "kyiv-01", "exp": 1735689600, "iss": "auth.bank.ua"}
S
Підпис (Signature)
RS256(base64(header) + "." + base64(payload), private_key) — цифровий підпис сервера
📋
Зареєстровані заяви (Registered Claims)
iss (видавець), sub (суб'єкт), exp (термін дії), iat (час видачі), aud (аудиторія), jti (унікальний ID)
🏦
Користувацькі заяви (Custom Claims)
role, branch, permissions, transaction_limit — бізнес-логіка банку

OAuth 2.0 — порівняння типів дозволів (Grant Types)

📱
Код авторизації + PKCE
Для: SPA, мобільні додатки
Безпека: найвища
Використання: основний потік для відкритого банкінгу (Open Banking)
🖥️
Клієнтські облікові дані (Client Credentials)
Для: сервер-сервер (M2M)
Безпека: висока (немає користувача)
Використання: API платежів, внутрішні мікросервіси
🔄
Токен оновлення (Refresh Token)
Для: оновлення access token
Безпека: rotation обов'язкова
Використання: тривалі сесії без повторного логіну
🏧
Авторизація пристрою (Device Authorization)
Для: IoT, POS, Smart TV
Безпека: середня (out-of-band)
Використання: пристрої без клавіатури

Застарілі: неявний потік (Implicit Grant, токен в URL) та пароль власника ресурсу (Resource Owner Password, передача пароля клієнту) — ЗАБОРОНЕНІ для фінансових систем.

Життєвий цикл токена

Від видачі до відкликання

1
Видача (Issuance)
Після автентифікації: access token (5-15 хв) + refresh token (24 год)
2
Перевірка (Validation)
Кожен запит: підпис, exp, iss, aud, scope — якщо невалідний → 401
3
Оновлення (Refresh)
Access token expired → refresh token → нова пара токенів (rotation)
4
Відкликання (Revocation)
Logout, зміна пароля, підозріла активність → token blacklist / Redis TTL
5-15 хв
TTL access token у банкінгу
24 год
TTL refresh token (max)
1 раз
Refresh token використовується одноразово

Session Fixation та інші атаки на сесії

Вектори атак та захист у фінансових системах

📌
Фіксація сесії (Session Fixation)
Зловмисник нав'язує відомий session ID жертві до логіну. Захист: регенерація ID після автентифікації
🕵️
Перехоплення сесії (Session Hijacking)
Перехоплення cookie через XSS, мережевий сніфінг. Захист: HttpOnly, Secure, TLS everywhere
🔁
Повтор сесії (Session Replay)
Повторне використання перехопленого токена. Захист: nonce, timestamp binding, короткий TTL
🌐
CSRF
Примусовий запит від імені жертви. Захист: SameSite=Strict, anti-CSRF токен, повторна автентифікація для критичних дій

Банківська вимога: для переказів > 10K грн — підвищена автентифікація (step-up auth) навіть при активній сесії.

🛡️

Ключові висновки

1️⃣ JWT потужний, але небезпечний — потребує правильної конфігурації
2️⃣ OAuth 2.0 + PKCE — стандарт для FinTech та Open Banking
3️⃣ OIDC = автентифікація — OAuth = авторизація, не плутати
4️⃣ Сесії у FinTech — короткі, прив'язані до контексту, з подвійним контролем (dual control)
