Лекція 3.3

RBAC, ABAC, ReBAC

Автентифікація vs Авторизація

🪪
Автентифікація
«Хто ви?»
Перевірка ідентичності
Логін + пароль + MFA
Відбувається один раз
✅
Авторизація
«Що вам дозволено?»
Перевірка дозволів
Ролі, політики, правила
Перевіряється при кожній дії

Касир = автентифікований. Але чи може він схвалити кредит на 10 млн грн? Це питання авторизації.

RBAC — Role-Based Access Control

Найпоширеніша модель у фінансах

💳
Касир
view_account, create_transaction (до 50K грн)
👔
Менеджер
+ approve_transaction, view_reports
🔍
Аудитор
view_all, generate_reports (read-only)
⚙️
Адмін
manage_users, manage_roles, system_config

Role Explosion: 10 відділень × 5 департаментів × 4 рівні = 200 ролей. RBAC не масштабується.

ABAC — Attribute-Based

Рішення на основі атрибутів та контексту

👤
Суб'єкт
Відділ, посада, рівень допуску, сертифікації
📄
Об'єкт
Тип даних, конфіденційність, власник ресурсу
🎬
Дія
Читання, запис, схвалення, переказ
🌍
Контекст
Час, IP, геолокація, рівень ризику

«Менеджер кредитування може схвалити кредит до 1M грн у робочий час з корпоративної мережі» — одна ABAC-політика замість 20 ролей.

ReBAC — Relationship-Based

Доступ на основі відносин (Google Zanzibar)

🏦 Банківський менеджер — бачить лише дані своїх клієнтів
👨‍👩‍👧 Сімейний акаунт — батько має доступ до акаунту дитини
🏢 Корпоративний банкінг — CFO → всі рахунки, бухгалтер → тільки операційний
🔧 Інструменти — OpenFGA, SpiceDB, Ory Keto
10M+
перевірок/сек у Zanzibar
<10ms
latency авторизації

Порівняння моделей

👔
RBAC
Простий, зрозумілий. Для невеликих організацій з фіксованою структурою
🧩
ABAC
Гнучкий, контекстний. Для складних політик з динамічними умовами
🕸️
ReBAC
Граф відносин. Для систем зі складною ієрархією власності

На практиці: гібридний підхід. RBAC для базових ролей + ABAC для контекстних політик + ReBAC для ownership.

Policy-as-Code та OPA

Open Policy Agent — політики як код

📝 Rego — декларативна мова для опису політик
🔀 Git — версіонування, code review, audit trail
🧪 Unit-тести — тестування політик як звичайного коду
🔌 Інтеграція — мікросервіси, API Gateway, Kubernetes, Terraform

Decoupling: зміна політики авторизації без перерозгортання жодного сервісу.

RBAC — приклад для банку

Ієрархія ролей банківської системи

1
Стажер (Trainee)
view_own_tasks — лише перегляд навчальних матеріалів та тестових даних
2
Касир (Teller)
view_account, create_transaction (до 50K грн), print_statement
3
Старший касир (Senior Teller)
+ approve_transaction (до 200K грн), override_limits, handle_disputes
4
Менеджер відділення (Branch Manager)
+ approve_loans (до 5M грн), manage_staff, view_branch_reports
5
Регіональний директор
+ view_all_branches, approve_loans (до 50M грн), strategic_reports

Ієрархічний RBAC: кожна роль успадковує дозволи нижчих рівнів. Менеджер автоматично має всі дозволи касира.

ABAC — приклад політики

Контекстне рішення для кредитного відділу

👤
Суб'єкт (Subject)
role = "credit_officer"
department = "lending"
clearance_level >= 3
certification = "risk_mgmt"
📄
Об'єкт (Resource)
type = "loan_application"
amount <= 2_000_000 UAH
risk_score < "high"
status = "pending"
🌍
Контекст (Environment)
time = "09:00-18:00"
day = "weekday"
network = "corporate_vpn"
device = "managed"
✅
Рішення (Decision)
action = "approve_loan"
effect = PERMIT
obligation: log_decision
obligation: notify_supervisor

Одна ABAC-політика замінює десятки RBAC-ролей. Зміна ліміту або часу — правка одного правила, а не перебудова ролей.

RBAC vs ABAC vs ReBAC

Коли застосовувати яку модель

👔
RBAC
Складність: низька
Гнучкість: низька
Масштабування: role explosion
Аудит: простий
Для: невеликі банки, фіксовані ролі
🧩
ABAC
Складність: висока
Гнучкість: максимальна
Масштабування: відмінне
Аудит: складний
Для: великі банки, регуляторні вимоги
🕸️
ReBAC
Складність: середня
Гнучкість: висока
Масштабування: графове
Аудит: візуальний
Для: multi-tenant, ownership

Рекомендація: RBAC для базових ролей + ABAC для контекстних рішень + ReBAC для ownership — гібридний підхід дає найкращий результат.

Policy-as-Code з OPA

Приклад Rego-політики для банківського API

📝 Rego-правило: allow якщо input.user.role == "manager" AND input.action == "approve" AND input.resource.amount < 1000000
🧪 Unit-тест: test_manager_can_approve_small_loan — перевірка з mock-даними перед деплоєм
🔀 CI/CD: git push → тести політик → conftest verify → автодеплой до OPA
📊 Decision Log: кожне рішення OPA логується — хто, коли, що запитував, результат
🔌
Інтеграція
API Gateway (Kong, Envoy), Kubernetes Admission, Terraform, мікросервіси через REST/gRPC
⚡
Продуктивність
Компіляція Rego у Wasm. Latency <1ms на рішення. Кешування partial evaluation
🛡️

Ключові висновки

1️⃣ RBAC — базовий — простий, але role explosion у великих організаціях
2️⃣ ABAC — контекстний — атрибути + середовище = точні політики
3️⃣ ReBAC — відносини — граф ownership для складних структур
4️⃣ Policy-as-Code — OPA/Rego = аудит, тестування, версіонування
