Де зберігати токени?

Рекомендації для FinTech

✅ Access token — у пам'яті (JS-змінна), короткий TTL (5-15 хв)
✅ Refresh token — HttpOnly Secure cookie, rotation при кожному використанні
❌ localStorage — НІКОЛИ для токенів у фінансових додатках
❌ URL параметри — НІКОЛИ, витік через Referer, logs, browser history

Атрибути безпеки Cookie

Повний набір захисних прапорців

🔒 HttpOnly — недоступний через document.cookie, захист від XSS-крадіжки
🔐 Secure — передається лише через HTTPS, захист від MITM-перехоплення
🌐 SameSite=Strict — не надсилається при cross-site запитах, захист від CSRF
⏰ Max-Age / Expires — короткий TTL (15-30 хв) для сесійних cookie
📍 Domain / Path — обмеження scope, не встановлювати на кореневий домен
🏷️ __Host- префікс — вимагає Secure + без Domain + Path=/ (найнадійніший)

Ідеальний cookie: __Host-session=abc; Secure; HttpOnly; SameSite=Strict; Max-Age=1800; Path=/

Порівняння сховищ для токенів

Де найбезпечніше зберігати credentials?

🧠
JS-змінна (пам'ять)
Недоступна іншим вкладкам. Зникає при F5. Найбезпечніше для access token
🍪
HttpOnly Cookie
Недоступний JS. Автоматично надсилається. Ідеально для refresh token
📦
sessionStorage
Ізольований по вкладці. Зникає при закритті. XSS все ще загроза
⚠️
localStorage
Персистентний, доступний JS. XSS = повна компрометація. НЕ для секретів

Патерн BFF (Backend For Frontend): токени зберігаються на сервері, клієнт отримує лише session cookie.

🛡️

Ключові висновки

1️⃣ HttpOnly + Secure + SameSite — обов'язкові атрибути cookies
2️⃣ localStorage небезпечний — XSS = повний доступ до всіх даних
3️⃣ Формджекінг — SRI + CSP + ізоляція платіжних форм
4️⃣ Access token у пам'яті — refresh у HttpOnly cookie з rotation
