Підробка міжсайтових запитів (CSRF)

Браузер автоматично додає cookies!

1
Жертва авторизована
Сесійний cookie банку активний
2
Відвідує evil.com
Або відкриває HTML-email
3
Прихований POST
Форма → bank.com/transfer
4
Банк виконує
Cookie валідний → переказ зроблено

Один відкритий email може ініціювати переказ коштів без відома користувача.

Захист від CSRF

🎫
CSRF Token
Унікальний токен у кожній формі. Зловмисник не може отримати його cross-origin
🍪
SameSite Cookie
Strict — cookie не надсилається з cross-site запитів. Найпростіший захист
🔄
Подвійне надсилання (Double Submit)
CSRF-токен у cookie і в тілі запиту/заголовку. Сервер порівнює обидва
📋
Власні заголовки (Custom Headers)
X-Requested-With потребує попередній CORS-запит (preflight). Блокує міждоменні запити

SameSite Cookie

Найефективніший захист від CSRF

🔒
Strict
Cookie НЕ надсилається при cross-site навігації. Максимальний захист
⚖️
Lax
Cookie лише для top-level GET. Компроміс між безпекою та UX
⚠️
None
Cookie завжди надсилається. Потрібен Secure. Для cross-site інтеграцій

Для фінансових систем: SameSite=Strict + CSRF Token для критичних операцій (переказів, зміни паролю).

Клікджекінг (Clickjacking)

Прозорий iframe поверх шкідливої сторінки

🖼️ Механізм: iframe з bank.com (opacity: 0) поверх fake-page.com
🖱️ Дія: клік на «Забрати приз» = клік на «Підтвердити переказ 50K грн»
👍 Лайкджекінг (Likejacking) — приховані кнопки «Подобається» соцмереж
🖱️ Курсорджекінг (Cursorjacking) — курсор відображається не там, де насправді

Один клік = підтверджена фінансова операція. Жертва навіть не бачить сторінку банку.

Захист від клікджекінгу

🏗️
X-Frame-Options
DENY — повна заборона iframe
SAMEORIGIN — лише свій домен
Простий, підтримується всюди
Legacy, але ефективний
🛡️
CSP frame-ancestors
frame-ancestors 'none'
frame-ancestors 'self'
Гнучкіший контроль
Сучасний стандарт

Обидва заголовки разом: X-Frame-Options: DENY + CSP frame-ancestors 'none' для максимальної сумісності.

CSRF у фінансових системах

Реальні сценарії та захист

💸 Переказ коштів — POST /transfer з прихованої форми на evil.com
🔑 Зміна пароля — POST /change-password без знання поточного
📧 Зміна email — прив'язка email зловмисника → reset password
🛡️ Захист: CSRF token + SameSite + re-authentication для критичних дій

Потік CSRF-атаки

Покрокова діаграма експлуатації

1
Розвідка
Зловмисник аналізує форму переказу: URL, параметри, метод
2
Підготовка
Створює HTML-сторінку з прихованою формою та auto-submit
3
Доставка
Фішинг-лист, коментар на форумі або реклама з посиланням
4
Виконання
Браузер жертви надсилає POST + cookie → банк виконує операцію
5
Результат
Кошти переведено. Жертва дізнається лише з SMS-повідомлення

SameSite Cookie — детальне порівняння

🔒
Strict
Cross-site навігація: ❌
Cross-site POST: ❌
Cross-site GET: ❌
Top-level GET: ❌
Використання: платіжні операції
⚖️
Lax (default)
Cross-site навігація: ❌
Cross-site POST: ❌
Cross-site GET: ❌
Top-level GET: ✅
Використання: загальна автентифікація
⚠️
None + Secure
Cross-site навігація: ✅
Cross-site POST: ✅
Cross-site GET: ✅
Top-level GET: ✅
Використання: виджети, OAuth

Chrome з 2020 року встановлює SameSite=Lax за замовчуванням. Це зменшило CSRF-атаки на 90%+.

Клікджекінг — структура шарів

Візуалізація атаки підміни інтерфейсу (UI redressing)

👁️
Що бачить жертва
Сторінка з грою або призом
Кнопка «Забрати виграш»
Привабливий дизайн
Нічого підозрілого
Довіряє своїм очам
🔍
Що відбувається насправді
iframe bank.com (opacity: 0)
z-index вищий за видиму сторінку
Позиція = точно над кнопкою
Клік потрапляє на «Підтвердити»
Переказ 50,000 грн виконано

Багатокроковий клікджекінг: серія кліків для заповнення суми, IBAN і підтвердження переказу.

CSRF у фінансових транзакціях

Критичні операції під загрозою

💸
Переказ коштів
Прихована форма POST /api/transfer з сумою та IBAN зловмисника
📱
Додавання отримувача
POST /api/beneficiary — додає рахунок зловмисника у «довірені»
🔓
Зміна лімітів
POST /api/limits — збільшення денного ліміту переказів
📧
Зміна контактів
POST /api/profile — email/телефон зловмисника для 2FA і відновлення

Захист: CSRF-токен + повторна автентифікація (пароль/OTP) для критичних операцій + SameSite=Strict.

🛡️

Ключові висновки

1️⃣ CSRF — браузер автоматично додає cookie, запит виглядає легітимним
2️⃣ SameSite=Strict — найпростіший і найефективніший захист від CSRF
3️⃣ Клікджекінг — прозорий iframe, захист через X-Frame-Options / CSP
4️⃣ Ешелонований захист (Defense in Depth) — CSRF-токен + SameSite + повторна автентифікація для переказів
