Типи тестування безпеки

🤖
Оцінка вразливостей (Vulnerability Assessment)
Автоматизоване сканування: Nessus, Qualys. Широко, але поверхнево
🎯
Тестування на проникнення (Penetration Testing)
Імітація атаки етичним хакером. Ручний аналіз + творчий підхід
🔴
Червона команда (Red Team)
Повномасштабна APT-імітація: фішинг + техніка + фізичний доступ
💰
Bug Bounty
Тисячі дослідників, оплата за результат, безперервний процес

PTES — стандарт тестування на проникнення

7 фаз пентесту

1
Підготовка (Pre-engagement)
Обсяг робіт, правила, юридичні аспекти
2
Розвідка (Recon)
Збір інформації: домени, IP, технології
3
Моделювання загроз (Threat Modeling)
Визначення векторів атаки
4
Експлуатація (Exploitation)
Експлуатація + пост-експлуатація

Фаза 5-7: Пост-експлуатація (латеральний рух, доступ до даних) → Звітування (вразливості, ризики, рекомендації).

OWASP Testing Guide

91 тест-кейс для веб-додатків

🔍 Збір інформації (Information Gathering) — ідентифікація технологій, виявлення, перелічення
🪪 Автентифікація (Authentication) — перебір паролів, стандартні облікові дані, парольна політика
🔓 Авторизація (Authorization) — IDOR, ескалація привілеїв, обхід шляхів
💉 Валідація вводу (Input Validation) — SQLi, XSS, ін'єкція команд, XXE
💼 Бізнес-логіка (Business Logic) — від'ємні суми, стан гонки (race conditions), обхід робочого процесу

Типи тестування за обсягом знань

⬛
Чорна скринька (Black Box)
Нуль інформації. Імітація реального зловмисника. Найбільш реалістичний
🔲
Сіра скринька (Grey Box)
Часткова інформація: облікові дані, API-документація. Оптимальний для FinTech
⬜
Біла скринька (White Box)
Повний доступ: код, архітектура, облікові дані. Максимальне покриття

Для фінансових систем: сіра скринька (grey box) — баланс між реалістичністю та ефективністю тестування.

Особливості та обмеження

🧪 Staging only — НІКОЛИ на production з реальними даними клієнтів

📝 NDA + договір — чіткі обмеження, kill switch для екстреної зупинки
🏦 QSA — Qualified Security Assessor для PCI DSS scope

Тестування на проникнення: фази детально

Від розвідки до звіту

1
Розвідка (Reconnaissance)
OSINT, перелічення DNS, Shodan, Google Dorking, збір email-адрес, субдомени
2
Сканування (Scanning)
Nmap (порти/сервіси), Nikto (веб), перебір директорій (ffuf/gobuster)
3
Експлуатація (Exploitation)
PoC-експлойти, SQLi/XSS, ескалація привілеїв, отримання shell-доступу
4
Пост-експлуатація (Post-Exploitation)
Латеральний рух, pivoting, доступ до БД, ексфільтрація тестових даних
5
Звітування (Reporting)
Резюме для керівництва, технічний звіт, CVSS-оцінки, PoC, рекомендації, план повторного тестування

Робочий процес Burp Suite

Основний інструмент веб-пентестера

🔄
Проксі (Proxy)
Перехоплення HTTP/HTTPS трафіку між браузером і сервером. Аналіз кожного запиту/відповіді
🕷️
Сканер (Scanner)
Автоматичне виявлення SQLi, XSS, SSRF, обходу шляхів. Активний та пасивний режими сканування
🔁
Repeater
Ручна модифікація запитів: зміна параметрів, headers, cookies. Тестування IDOR, auth bypass
💣
Intruder
Автоматизований brute force: credential stuffing, parameter fuzzing, ID enumeration

Додаткові інструменти: OWASP ZAP (безкоштовний), Postman (API), sqlmap (SQLi), Nuclei (templates).

Automated vs Manual Testing

Порівняння підходів до тестування безпеки

🤖
Автоматизоване
SAST: SonarQube, Checkmarx
DAST: ZAP, Burp Scanner
SCA: Snyk, Dependabot
Швидко, масштабовано
Багато false positives
Не знаходить бізнес-логіку
🧑‍💻
Ручне
Code review експертами
Manual penetration testing
Business logic testing
Глибоке, творче
Менше false positives
Повільно, дорого, не масштабується

Оптимальна стратегія: автоматизація для L1 (CI/CD) + ручне тестування для L2/L3 (бізнес-логіка, складні сценарії).

Структура звіту аудиту

Audit Report Template

📄 Executive Summary — загальна оцінка ризику, ключові знахідки, 1-2 сторінки для керівництва
📊 Scope & Methodology — що тестували, як тестували, які інструменти, часові рамки
🔴 Findings — кожна вразливість: опис, CVSS, PoC (скриншоти), вплив на бізнес, affected URL/endpoint
✅ Recommendations — конкретні кроки виправлення для кожної знахідки з пріоритетом та SLA
📈 Risk Matrix — зведена таблиця: Critical/High/Medium/Low з кількістю та статусом

Звіт повинен бути actionable: розробник має зрозуміти що виправити, менеджер — який ризик для бізнесу.
