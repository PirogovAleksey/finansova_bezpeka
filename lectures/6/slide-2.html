Три рівні ASVS

🟢
L1: Базовий (Opportunistic)
Автоматизоване тестування. Мінімум для будь-якого додатку
🟡
L2: Стандартний (Standard)
Для чутливих даних. Ручне тестування + огляд коду. Більшість FinTech
🔴
L3: Просунутий (Advanced)
Критичні системи: core banking, SWIFT, платіжні процесори. Моделювання загроз + повний пентест

Інтернет-банкінг → L2. SWIFT-інтерфейс, process acquiring → L3. Маркетинговий сайт банку → L1.

Категорії ASVS

14 розділів, 280+ вимог

V1 Архітектура (Architecture) — моделювання загроз, принципи безпечного проєктування
V2 Автентифікація (Authentication) — 60+ вимог: MFA, парольна політика, зберігання облікових даних
V3 Управління сесіями (Session Management) — таймаут, фіксація, паралельні сесії
V4 Контроль доступу (Access Control) — RBAC/ABAC, запобігання IDOR, принцип найменших привілеїв
V5 Валідація (Validation) — обробка вхідних/вихідних даних, кодування, санітизація
V6 Криптографія (Cryptography) — алгоритми, управління ключами, TLS

ASVS L1 / L2 / L3 порівняння

Що вимагає кожен рівень

🟢
L1: Базовий (Opportunistic)
~130 вимог. Автоматизований SAST/DAST. Базова валідація вводу, HTTPS, хешування паролів. Достатньо для маркетингових сайтів
🟡
L2: Стандартний (Standard)
~230 вимог. Огляд коду, моделювання загроз, MFA, управління сесіями, безпека API, безпечний SDLC. Стандарт для інтернет-банкінгу
🔴
L3: Просунутий (Advanced)
~280 вимог. Повний пентест, HSM для ключів, захист від модифікації, безпечне завантаження, повна модель загроз. Для core banking, SWIFT

Як формулювати вимоги на основі ASVS

V2.1 Паролі: мінімум 8 символів, максимум 128, перевірка через Have I Been Pwned API, bcrypt/argon2 для хешування
V3.4 Cookie: Secure, HttpOnly, SameSite=Strict, prefix __Host-, session timeout 15 хв для банкінгу
V4.2 Доступ: заборона за замовчуванням, серверна перевірка, запобігання IDOR через непрямі посилання
V6.2 Крипто: TLS 1.2+ обов'язково, AES-256-GCM для даних at rest, RSA-2048+ або ECDSA для підписів
V13 API: OAuth 2.0 + PKCE, rate limiting, schema validation, Content-Type enforcement

Кожна вимога ASVS має ID (наприклад, V2.1.1) — зручно для трекінгу відповідності у Jira / Confluence.

Впровадження ASVS у проект

Покроковий план інтеграції

1
Аналіз прогалин (Gap Analysis)
Аудит поточного стану: які вимоги ASVS вже виконані, які ні. Чеклист у Excel/Jira
2
Визначення рівня
Обрати L1/L2/L3 залежно від критичності системи та вимог регулятора
3
Дорожня карта
Пріоритизувати вимоги за ризиком: критичні (автентифікація, криптографія) першими, бажані — останніми
4
Автоматизація L1
SAST (SonarQube), DAST (OWASP ZAP), SCA (Snyk) інтегрувати у CI/CD pipeline
5
Регулярний аудит
Щоквартальний перегляд відповідності, оновлення чеклиста при нових версіях ASVS
